# 主流程需求输入契约

前端默认进入新需求页；`?legacy=1` 保留旧审阅页面。新页面连接 `productDevelopmentWorkflow`，创建输入为 `brief/iterationId/guidedIntake:true`。旧输入默认跳过澄清。

流程：方案摘要与显式假设 → 关键问题卡片 → 回答后可再次完善方案 → 完整产品稿 → 版本确认 → 原有项目范围授权。最多四轮方案分析，不自动选择推荐答案，不自动批准产品稿。必答项必须有回答；选择以服务端选项 ID 校验，补充答案使用独立文本。回答携带方案 hash、操作者与动作，最终完整稿的 hash 绑定澄清历史。用户确认的是业务选择，不是研发/发布授权。

需求与产品审核页面将左侧保留给主流程导航，中间阅读方案或完整产品稿，右侧展示当前待决项、逐项回答和固定提交区；长问题在侧栏内滚动，不影响成果阅读与确认入口。小屏改为纵向内容并提供直达澄清区的入口。页面显示当前轮已回答数与必答缺口，不将它解释为需求覆盖度、能力成熟度或研发完成进度；完整需求是否充分仍由产品稿审阅确认。

`/intake-api/runs` 创建/列举主 Run，`/intake-api/runs/:runId` 回读，`/intake-api/runs/:runId/respond` 提交澄清或产品批准/拒绝。服务端校验当前步骤、版本、模型模式、完整答案与 Origin 后恢复；页面可刷新恢复当前 Run，不自动重试写操作。状态事实只归 Mastra LibSQL；HTTP 返回的是业务投影。已有生成失败 Run 提供明确状态，可通过 Studio 排查，当前不承诺生成中故障自动续做。

## 远端同步设置

工作台右上角“远端同步设置”管理**后续节点**的交付副本去向：产品与业务澄清、技术方案、开发与评审、测试、发布可分别关闭同步或选择目标仓库。初始默认全部指向 HRM 项目仓库，保持单项目行为。页面会展示每个已登记仓库的远端地址，便于核对“HRM 项目仓库”实际指向；不会泄露本地 checkout 路径。目标仓库只能由实践服务的 `MASTRA_REMOTE_SYNC_TARGETS` 环境变量登记；页面不能新增路径、远端地址或凭据。

“项目仓库管理”页是仓库字典入口，可添加、编辑或移除本机已授权的项目 checkout；保存时服务端核验 Git 根目录与无凭据 HTTPS origin，不会自动 clone、改写代码或推送。阶段页只负责从字典分配去向。也可通过 `MASTRA_REMOTE_SYNC_TARGETS` 作为首次启动的环境初始值。每个目标的 `root` 必须是 Git 根目录且 `origin` 精确匹配登记地址；同步仍使用隔离 Git index 和 `codex/workflow/<根RunId>` 分支。关闭某阶段时，该阶段不创建远端交付副本，Workflow、审批、预算和恢复事实仍由 LibSQLStore 保存。

当前设置的粒度是 Workflow 阶段，动态开发团队内部的前端、后端、工程角色还没有独立的同步节点，不能声称已经支持“按角色分仓”。后续要支持时，应由角色交付产物附带稳定角色路由键，再在服务端目标注册表中设置映射；不接受浏览器提交路径或 Git 配置。

无新增真实身份、跨实例协调、视觉图库或附件能力。固定模式只验证流程，不理解输入。真实质量需要独立业务样本验收。

## 2026-11-08 故障阶段提示与严格执行路径

开发可恢复故障使用专门卡片：显示发生阶段、公开原因、已保留信息和下一步建议；用户填写确认人后直接选择“重试技术方案生成”等具体动作或“停止本轮流程”，补充说明可选，二次确认后才提交。内部 phase/role/kind 默认折叠为技术信息。运行/失败提示从原生具体阶段读取，不把提交响应成功当作业务执行成功。

正式开发图使用原生条件分支，未命中阶段不执行。模型故障在实际阶段暂停，不再继续空跑组队、自检、评审等后续业务节点；恢复使用原生 suspendData 中失败后的状态，保留预算、源码检查点和已完成任务。停止开发后主流程保存阻塞终态，测试、发布与最终交付不启动。再次故障耗尽人工恢复预算时真正抛出异常，原生引擎记为 failed。

可恢复故障的原生状态是 suspended（等待决定），不是 failed；该阶段未成功，前端据实显示“未完成”。历史 recover-development 暂停点仍兼容，历史已保存的 Completed 不重写。状态映射节点 state-after-* 只是控制流，不能当作业务执行完成。详见[决策](../../docs/decisions/2026-11-08-mastra-stage-state-flow.md)。

## 2026-11-08 模型超时细项与架构时限

架构角色采用版本化 `development-timeout.v2` 策略：单个模型步骤300000ms、一次 Agent 执行总计600000ms；其他角色保持90000ms/180000ms。策略复用原生 `modelSettings.timeout`，不增加自建计时器，不改变两次自动尝试、一次人工恢复、72次角色调用与方案审批限制。每次自动尝试各自使用上述 Agent 时限，不是整轮需求的总时限。

故障增加可选 `modelCall`，包含策略版本、步骤/总时限、本地单调时钟记录的实际耗时、UTC记录时间、角色调用序号，以及来源白名单。Mastra超时保留实际 `timeoutType/timeoutMs`；HTTP408/504/524记为上游超时，连接/响应头/传输超时独立分类。普通Abort或缺少细项的Timeout不按耗时推断触发时限。角色调用序号沿用现有预算计数，不等于上游HTTP请求数或计费数量。

重试耗尽时抛出应用自己的 `DevelopmentStageFailure`，其 `error.details` 保存最多八条最近尝试的白名单诊断、完整故障数与调用计数。该属性由原生 Mastra Error 序列化进入Store，避免最终异常只留下预算文案而丢掉最后失败尝试。不附带业务源码、请求/响应、URL、headers或原始cause。暂停卡片技术信息和失败页面“查看模型调用诊断”显示这些来源及耗时。

## 如何区分预算暂停和同步失败

- 模型调用额度耗尽：原生 `recover-development` 关口显示“补充调用额度并继续”，可填写本次追加次数（1–72，默认72），填写确认人并再次确认后追加；累计计数、成功任务和原文件权限保留。
- 单次资料读取、模型消息或资料目录预算不足：进入原生预算暂停卡，显示类型、触限字节量和当前档位；“补充资料预算并继续”明确提高下一档（每档翻倍、最多4档），只重新调用当前阶段。若工具错误被模型捕获仍不能发布缺资料结果。达到本地上限后可缩小材料再按当前上限重试，或停止；增加本地字节额度不保证上游模型容量。
- 角色资料同步失败：显示“重试资料同步”，版本及缓存校验后只同步已保存产物，不重新调用模型，不替代产品或开发批准。历史未实施且保存了阻塞架构结果的失败记录通过固定 Time travel 入口恢复；缓存缺失或源码漂移时拒绝重跑。没有恢复入口不等于预算耗尽。

预算恢复使用已有原生版本hash、源码检查点和身份预检，服务端拒绝跳档、跨预算类型追加及过期决定；追加历史、累计调用消费和资料预算档位持续保留，产品修订后的重新规划也继承。恢复指重试当前业务阶段，不代表从模型内部已生成的token继续。
