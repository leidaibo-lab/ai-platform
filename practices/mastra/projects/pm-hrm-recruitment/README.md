# Mastra 招聘管理工作流验证项目

## 目标与分工

以 `pm-hrm` 招聘模块为业务场景，在一个持续项目里验证从诉求、澄清、产品稿、人工确认到开发和测试的产研流程。

用户提供诉求、业务资料及明确约束，作必要业务决策；Mastra 产品 Agent 负责梳理需求、发现缺口、提出澄清、形成产品稿及验收标准。产品稿是否合适本身就是考查内容，不能由外部助手先写完规则和验收再交给 Agent 改写。我们负责观察、评审和记录实际表现，具体产品版本由用户在 Workflow 中确认。

## 本轮输入

唯一提交给产品 Agent 的业务输入为 [原始诉求](./sources/brief.md)。不把本项目说明、评审依据、参考答案或上轮整理的验收清单附到输入中。产品 Agent 保持现有角色提示词与需求交接 Skill，不为本轮预先补写业务答案。

用户于 2026-11-05 已选择：

- 首期为候选人初筛与邀约记录，不进入面试安排。
- 使用预置合成职位及候选人数据。
- 使用本地模拟角色和人工审批标签，暂不建设真实账号认证。

其他字段、状态、权限、页面及验收细则由 Agent 根据实际提供的资料分析，建议与待决项不能冒充用户已确认规则。

## 资料与当前能力边界

业务参考来自同级 `pm-hrm` 仓库招聘模块；本项目不修改源仓库、不共享业务数据库。源仓库产品文档可以作为后续调研资料和评审依据，不自动成为本轮已加载上下文。

2026-11-06 起，四个产品角色通过原生 Workspace 只读 `sources/` 中的业务材料；目前仅含原始 brief，未挂载 pm-hrm 源仓库。本 README、历史评审和评分量表均不在 Agent 资料区。**配置可读目录不代表模型已实际读取**，新 Run 需检查原生文件工具结果。下面 2026-11-05 的历史观察仍按当时无文件工具的条件解释。配置、产物导出与资料评测见 [Workspace 说明](../../workspaces.md)。

当前已另建受限开发Workflow和全栈评测试点，恢复/来源门禁及48项真实模型结果见[研发续办记录](../../evaluations/development/continuation-2026-11-06.md)。本招聘项目尚未把已批准产品版本交接到真实业务仓库，测试阶段仍只生成计划；不能把能力评测的生成交付或主持基准当作本项目功能已完成。

## 产品阶段怎样考查

评审以下表现，不将具体答案预先传给 Agent：

| 维度 | 观察问题 |
| --- | --- |
| 理解诉求 | 是否保留用户目标和三项已确认边界，有无擅自扩张或重复询问 |
| 主动分析 | 是否从招聘协作问题识别角色、交接、规则、失败和历史需求，而不只是复述诉求 |
| 事实与缺口 | 是否区分已知、建议和未决项；未读取资料时是否坦诚，是否提出会影响结果的具体问题 |
| 产品稿质量 | 阅读者能否理解要做什么；验收能否判定结果，未知项有无被伪装为已批准规则 |
| 交互与修订 | 澄清后是否正确修订并保留未解决项；能否在用户确认具体版本后交接下游 |

首稿允许存在合理待澄清项；发现关键信息缺失是能力表现，编造业务决定不是。生成成功、流程暂停、文档质量及工程验收分别记录，不能互相替代。

## 已确认的开发目标（2026-11-06）

用户指定业务仓库为[leidaibo-lab/hrm](https://github.com/leidaibo-lab/hrm)，采用pnpm monorepo，并确认以下划分：

- `apps/web`：Next.js业务前端。
- `apps/api`：NestJS业务API。
- `packages/database`：Prisma schema、客户端及迁移。
- Mastra产研编排继续留在本ai-platform仓库；不搬入hrm业务服务。

本轮只建立目标仓库工程骨架、环境健康检查与Docker Desktop Compose入口，业务范围仍取自用户在产品Workflow中批准的版本。新仓库不复制Ticket评测实现、隐藏断言、模型凭据或现有业务数据库。pnpm管理唯一根锁文件，包间使用`workspace:*`；Docker显式使用`desktop-linux`，本地预览保留项目数据，不套用一次性评测结束即清理的策略。

目标仓库登记不代表当前受限DevelopmentExecution已具备任意Git克隆、提交、推送或Docker工具权限；这些仍是组织者的工程操作，不能给被评Agent隐式开放。后续需要绑定产品Run/hash、仓库基线commit、批准路径及具体任务，再进入业务开发。
