# 以业务验收为完成条件的 Workflow 改造设计

状态：设计稿，2026-11-10。本文把本轮用户指定的五项方向转成实现边界与验收条件，尚未接入运行时；不改变当前 Run 的审批、预算或成功含义。[方案取舍](../../docs/decisions/2026-11-10-mastra-business-delivery.md)。

## 1. 完成意味着什么

一个业务版本交付完成，需要同时满足：本期规则明确并获确认；实际业务身份能连续完成批准旅程；关键拒绝和异常符合规则；执行证据绑定同一需求、候选、测试和运行环境；发布结果能够关联到该候选。文档、模型评审和人工批准分别证明各自事实，不能互相替代。

“真实角色”指实际参与系统授权的身份及其资源责任，不要求测试使用真实员工或真实候选人。合成账号可以验证真实认证及职位授权；角色下拉框只能证明模拟角色体验。记录中必须区分模拟身份、隔离测试账号和真实试点，不能由模拟切换推断认证通过。

本期不要求统一替换 HRM 认证、不接管外部生产发布、不扩展探索主线 Runtime、不创建第二个审批库。业务系统缺少认证时仍可交付明确限定的模拟版本；真实资料试点的准入继续保持未满足。

### 当前证据与缺口

| 位置 | 当前实现 | 本设计改变的判断 |
| --- | --- | --- |
| [初始澄清](src/intake/contracts.ts)及[页面](web/src/IntakeApp.tsx) | 已取消 round/history 四轮限制，继续 refine 与显式 finalize 分开 | 不设澄清总轮数预算，不证明需求已经成熟 |
| [产品子流程](src/mastra/workflows/product.ts) | closure 在 writing 前，publish 随后生成产品产物 | 独立审查必须消费写作后的确切交付包 |
| [开发方案](src/development/v2/contracts.ts) | 任务按文件分工，要求全部产品行号引用有覆盖 | 行号覆盖用于定位；业务旅程需要独立验收依据 |
| [浏览器 QA](src/browser-qa/runner.ts) | 只运行静态 HTML，不支持动态全栈 | 全栈必须由同版本启动 Adapter 提供隔离目标 |
| [固定检查](src/development/v2/contracts.ts)及[质量门](src/delivery/testing.ts) | HRM 登记 check/build/smoke，用例可映射套件退出结果 | 基础工程检查通过不能自动证明业务断言通过 |
| [最终交付](src/mastra/workflows/product-development.ts) | 已有源码、质量、发布和健康散列绑定 | 保留这些校验，增加逐旅程执行与覆盖缺口校验 |

fixture 与 live 始终分别呈现。fixture 驱动真实浏览器或容器仍只证明相应执行机制，不升级为真实模型业务交付证据。

## 2. 澄清按业务依赖推进，不设总轮数上限

保留 Mastra 原生 suspend/resume。人工回答是事实，模型摘要和推荐不是事实。单轮问题数继续作为交互限制；不因问满或问够轮数而切换成熟状态。

### 决策和状态

拟新增版本化 ClarificationState，明确记录 confirmedScope、decisions、openDecisions、affectedJourneys与 historyRefs。每项决策包含稳定 ID、问题、适用范围、建议、显式回答来源、被替代决策及所影响需求；未回答时回答引用为空。摘要可重新生成，原问题与答案保持不可变。

状态采用 collecting、ready-for-draft、stopped。ready-for-draft 只表示可编写当前确认范围的稿件；产品可开发性仍由写作后的交接审查决定。阶段跳转由宿主代码判定，模型只能提出缺口和证据。

- 每轮先核对历史答案与当前依赖，优先范围、责任和流程，再细化字段与异常。未解决的问题保留 ID，不为换一种表述重新创建已确认事项。
- 新答案与旧规则冲突时保留双方来源，只暂停受影响旅程；不能静默采用最新一句或推荐选项。
- 不设澄清总轮数或累计费用/调用预算关口。单次运行保护触发时保留检查点，说明原因并沿现有失败恢复继续；资源限制不判断需求成熟度。
- 用户可继续当前 Run 或停止；已保存回答保持，不重新提交 brief，不重做已确认步骤。重复提交由原版本门禁拒绝。
- 用户可明确选择缩小范围。系统展示移除能力、关联页面、验收和目标影响；显式确认新范围版本后才排除，不能从讨论次数或资源限制推导删需求。
- 用户要求生成阶段草稿时允许输出，并显示它仍不可开发；关键未决不能因生成正文而消失。

持久化历史可以分页读取；模型输入用可追溯摘要与按需原文，不能用无限增长全文解决四轮限制。摘要缺失或冲突必须回读依据，不能把压缩内容当成新的批准来源。

## 3. 写作后独立审查最终交接包

新增独立只读审查调用，输入仅为最终正式包、确认决策与来源版本、需求—验收映射。使用独立执行上下文，不能由写作者自报审查通过；可复用已有闭环方法，但审查任务与写作任务分开保存。

正式包按读者需要提供项目总览、模块 PRD、验收配套和必要设计引用；小范围可以合在一个文档，不能把文件数量设为质量门。内部问题、决策经过、方法使用记录、模型日志进入内部材料。正式包的核心规则须能独立理解，引用内部记录只作溯源。

### 审查输出及处置

ProductHandoffReview 绑定 packageHash、decisionBaselineHash、审查方法版本和实际调用证据；输出 findings、unchecked、requirementCoverage。发现必须有受影响规则、精确位置、具体歧义或缺失及推荐路由。模型结论属于评审证据，不属于批准事实。

| 发现 | 去向 | 继续条件 |
| --- | --- | --- |
| 已确认规则在写作中丢失、互相冲突，或操作/验收描述不完整 | 写作修订 | 按已有依据修复，重新审查最终包 |
| 缺少业务决定，或修复会改变范围、权限和结束条件 | 澄清 | 保存未决及影响；用户明确回答后生成新版本 |
| 设计附件不存在、链接错误或正文依赖聊天 | 对应交付责任 | 补齐可用附件，或让正文独立完整；不能用占位引用通过 |
| 环境、模型或预算导致未完成审查 | 保留检查点 | 恢复审查；未执行不能当成无发现 |
| 全部本期要求有明确规则和验收，无阻断或未审范围 | 产品人工确认 | 人工批准确切 packageHash；独立审查不代替批准 |

审批分清“认可方向/范围”和“批准可开发基线”。方向认可不能授权代码执行。可开发基线只覆盖已确认且完成交接审查的旅程；未决部分要么继续澄清，要么由用户明确排除并形成新基线。低风险延期须有依据，不能以人工勾选绕过当前必需行为。

原始澄清后的写作、开发阻塞后的修订、人工退回后的重写均走同一交接审查入口。任何正式包字节改变都使旧审查与批准失效，不只给首次生成加节点。

## 4. 用纵向旅程组织交付，保留专业分工

不强制每个任务都修改前后端和数据库。增加 JourneyContract，由产品规则派生；技术任务引用旅程，旅程通过多个专业任务共同实现。仅文案等小任务仍可单独处理。

| JourneyContract 内容 | 必须回答的问题 |
| --- | --- |
| id、requirementRefs、acceptanceRefs | 属于哪个已批准行为，怎样判定完成 |
| actor、assignment、preconditions | 谁对哪个资源有责任，什么条件下可进入 |
| entry、actions、input | 从哪个页面或 API 入口输入什么、执行什么 |
| guards、forbiddenTransitions | 服务端如何拒绝越权、跳步或不适用动作 |
| committedFacts、history | 成功提交哪些事实，历史怎样保留 |
| nextActor、nextTask、completion | 下一位责任人从哪里接续，怎样结束本旅程 |
| exceptions、retry、duplicate | 取消、拒绝、重复与失败后，事实及下一步是什么 |
| verificationRequirements | 哪些观察必须来自 UI、API、持久化或人工业务验收 |

这些字段承载产品语义，不能自动填入未经确认的招聘政策。未适用项记录依据，不能机械要求所有旅程都产生待办。

架构方案同时输出旅程、专业任务、依赖和集成验收责任。任务的路径不重叠只能证明合并可行；是否可以并行还取决于接口和数据契约是否明确。实现者交付专业任务，集成检查消费合并后候选；全部文件完成不等于旅程完成。

以招聘作为验证样本时，至少检查：录入后 HR 筛选、负责人初筛、邀约不同结果、面试安排、评价、后续决策的接续；多轮、多人、提前决定、终态等预期取自最终确认版本，不在 workflow 中固化答案。测试应直接操作浏览器发现“继续后没有入口”“展示选项与提交值不同”等缺陷。

需求采用稳定语义 ID，原文行号保留为位置引用。标题、方法说明和讨论记录不再作为必须编写业务测试的要求；原文归类由产品输出和独立审查核对，不能自动过滤含否定或未决词的行。每个本期业务要求都必须映射旅程及适用验收。

## 5. 测试与实际技术栈一致

保留静态 HTML Adapter，新增独立版本的全栈执行档，不把任意宿主 URL 塞进原 BrowserCase。优先组合已有 Docker/Compose 候选验证与 Playwright，不自写浏览器驱动、服务调度或数据库。

### 候选生命周期

1. 宿主校验已批准产品、方案、测试包和实际源码快照，构建不可变候选镜像；测试包版本参与验证绑定，但不改变应用源码的定义。
2. 为该测试执行创建独占网络、数据库、容器名和合成数据集；运行冻结迁移，再执行 seed，最后等待 API/Web 就绪。迁移失败明确阻塞，不退回用户已有数据库。
3. 宿主把运行句柄交给受限测试 Adapter；模型只选择已批准用例 ID，不能指定端口、URL、shell、数据库或身份凭据。
4. 通过真实 Web→API→数据库链路执行用例。每个身份独立浏览器上下文；跨角色旅程共享该用例的合成业务对象，不能共享登录态。
5. 每项关键操作后验证页面结果、服务端拒绝/提交结果与必要的持久化事实；API/数据库验证通过固定断言工具执行，不能以截图替代。
6. 收集步骤、断言、日志摘要、截图及事实断言结果，在 finally 清理本次容器、网络及临时卷；失败或超时同样清理，清理失败保留资源 ID 并提示人工处理。

用例之间默认重建合成数据；确需共享状态的步骤属于同一个旅程用例，不依赖测试排序。进程重启后不得信任旧运行句柄：校验候选、镜像、环境和测试版本后，重新创建环境并从用例起点执行，不把中断前半段拼成通过。

### 执行上限与网络

动态测试显式批准新执行档、总时限、用例/步骤/断言与截图预算，不复用静态版的“三例十二动作”作为全栈能力上限。预算不足显示未测范围，不截断后声称旅程通过。预算是 Run 冻结政策，不能出现页面、工厂和测试器三套默认值。

仅候选服务、隔离数据库及测试运行器之间允许必要通信。浏览器不继承个人 profile、真实员工登录态、模型 key 或宿主 .env。候选无 Docker socket、宿主目录和业务数据库挂载；宿主不信任候选返回的外部重定向或资源 URL。若为浏览器提供回环转发，目标由宿主独占分配、绑定容器身份并限制外联，不接受用户输入的已有服务地址。

回执记录 environmentId、adapterVersion、实际镜像 digest、migrationHash、datasetHash、identityMode，以及测试/源码/需求版本。环境 ID 只用于追溯，不能当成版本散列。真实认证不足的用例标明 simulated；需要认证隔离的验收保持 blocked，不允许切换 role 参数后宣称已完成。

### 断言与结果

动作与断言需要有序交错，支持选择值、身份切换、等待和文本/可用性断言；不是所有动作结束后只看一个成功文案。终态包含 passed、failed、blocked、not-run。外部依赖缺失、测试未运行或超时均不能通过；截图是辅助证据，断言集合及观察来源必须完整。

## 6. 受控增加业务测试，保护原有检查

继续保护 check/build/smoke、依赖与锁文件；新增测试通过独立测试包进入候选环境。不能为了增加业务覆盖给实现者开放固定脚本修改权或任意 shell。

1. 独立测试角色依据批准规则设计测试，声明需求/旅程/断言及所需能力；与开发输出对照时，不能把当前实现行为直接转成预期。
2. 测试包进入单独只读评审，确认期望来自已批准规则、未删除既有断言、存在负向路径、无跳过和无条件通过。具有实质行为的测试需要代表性错误候选验证其能失败；不能声称该检查能证明任意语义。
3. 由测试负责人批准具体 testPackageHash、执行档和能力子集。只允许在测试命名空间新增文件；测试包通过隔离 Adapter 运行，不能回写源码、检查或用户仓库。
4. 测试包改变后重新评审与批准，并使旧测试结果失效；源码修复后保留原断言，重跑受影响旅程与共用回归。业务规则改变则先修订产品基线。
5. 不支持的测试能力形成明确缺口；不得把 browser/API/持久化用例改挂到 build 或健康 smoke 上放行。

拟新增 TestPackage：版本、productHash、journeyRefs、caseSpecs、fixtureRefs、adapterProfile、capabilities、reviewRef、approvalRef 与内容散列。测试源码若必要，按不可信代码隔离执行；“已评审”不等于拥有宿主权限。测试作者可以提出环境需求，宿主只从已登记执行档解析，不执行模型生成命令。

每个实际断言产生 assertionId、caseId、status、observationRef；基础工程检查只产生基础检查结果。CoverageGap 记录 requirementRef、journeyRef、缺少的观察、原因和影响。不能因所有引用都挂在同一套件上，就给这些业务用例批量标为 passed。

## 7. 同版本证据与最终门禁

Mastra Store 仍是运行与批准事实源。交付清单只由这些事实派生，文件投影不能反向授予批准或修改结果。

| 绑定 | 内容与失效条件 |
| --- | --- |
| 产品包 | 正式文档字节、语义要求、确认决策版本；规则或正文变化重新审查和批准 |
| 技术方案 | 产品包、旅程、任务、接口和执行授权；方案变化重新做受影响就绪与批准 |
| 候选 | 实际应用源码快照，基线 commit 及候选 commit 单独记录；不能仅凭分支名匹配 |
| 测试包 | 用例、期望、数据集、能力与批准；变化后重新批准并执行 |
| 执行环境 | 实际镜像、迁移、依赖/锁、数据集和 Adapter；差异使相关环境证据失效 |
| 质量记录 | 逐用例/断言结果、缺口、独立评审和人工结果来源；不能沿用旧源码结果 |
| 发布 | 经验证候选到制品的构建关联、部署回执、健康与回滚信息；来源不明的已有服务不算同版本 |

散列由宿主规范化序列化并重算，不由 Agent 自报。当前源码散列与未来实际 commit 可能发生在不同步骤，不能要求它们字面相等；需要验证候选 commit 中受控文件与已测快照一致。应用源码和测试包分别取散列，最终验证绑定同时包含二者。

拟新增业务完成判断，同时保留当前质量/发布校验：

- 所有本期必需旅程有对应通过结果，要求的观察层均已实际执行，无失败、阻塞或未执行项。
- 没有影响当前交付的覆盖缺口和未解决发现；范围排除必须回到产品显式确认，不能在质量门标记“接受风险”来消除必需验收。
- 结果绑定确切需求、候选、测试及环境版本；审批人标签、模拟身份与机器证据分别标明。
- 外部人工发布回执只能支持“依据人工回执确认发布”的表述；缺少机器构建关联时，不能展示“机器验证同版本发布”。

分别展示过程状态、业务验收状态、发布证据等级与试点适用范围。fixture、模拟业务通过、隔离账号业务通过、真实试点效果验证不是依次自动升级的总分。界面不得只用一个绿色“已完成”抹掉这些区别。

| E：完成与显示 | src/mastra/workflows/product-development.ts、src/delivery/{deployment,repository-assets}.ts、工作台结果视图 | 业务/过程/发布等级分开，缺口和版本漂移不能通过 |

批次互相依赖：C 可先用静态/受限 API 样本验证测试包机制，D 完成后才声称支持 HRM 全栈浏览器；E 依赖 A–D 的实际证据，不先改变成功标签。每批次以代码、恢复回归和相应真实执行证据交付，不能用本设计代替实现。

使用新的工作流/契约版本。旧 Run 保留原图、原散列和原能力声明；不自动加字段重新解释旧批准。部署新图前确认历史执行是否仍由旧版本承接，不能热重载正在运行的 live Run。

旧 Run 需要进入新流程时，显式登记迁移来源与已批准材料，新建运行关联；已确认业务可以带来源复用，但新产品包、方案、测试、执行能力和发布关系按新契约重新核实。迁移不复制旧通过结果充当新证据。

## 9. 验收场景

以下均为未来实现验收，尚未执行。机制回归用固定模型及原生 Store；需要真实进程的项目另列，不能以 mock 通过替代。

| ID | 场景 | 预期与证据 |
| --- | --- | --- |
| BD01 | 超过四轮仍有关键缺口 | 可继续；历史答案保留，不被迫生成完整稿 |
| BD02 | 超过四轮后关闭并重开服务 | 历史和当前方案完整保留，可继续；旧版本重复提交被拒绝 |
| BD03 | 讨论持续多轮，用户未确认缩小范围 | 不删除能力、不默认采用建议、不产生可开发批准 |
| BD04 | 新答案与已有规则冲突 | 显示双方来源和受影响旅程，其他确认保持；不会静默覆盖 |
| BD05 | 写作漏掉一条已确认拒绝规则 | 写作后审查定位遗漏，修订并重新审查；旧审查不能批准新正文 |
| BD06 | 正式包依赖聊天、含方法日志或无效原型 | 交接审查指出读者无法执行的位置；修复后正式包可独立阅读 |
| BD07 | 开发阻塞修订了产品 | 修订稿也走交接审查，原方案/质量不能沿用 |
| BD08 | 前后端任务均完成，但下一角色没有入口 | 集成旅程验收失败，不由任务完成数放行 |
| BD09 | 展示选项与 POST 值不同，或继续动作无下一入口 | 浏览器有序操作与 API/事实断言失败，不能凭 API 正常路径通过 |
| BD10 | 有两个同角色身份、两个资源责任范围 | 分别验证可见/可操作及越权拒绝；仅角色下拉框不算身份隔离 |
| BD11 | 动态候选迁移或 seed 失败 | blocked，保留实际失败证据并清理独占资源；不连已有数据库 |
| BD12 | 一个角色操作后另一个角色接续 | 独立登录上下文看到同一对象已提交结果和正确下一任务 |
| BD13 | 测试环境故障、超时或中断重启 | 不拼接半次通过结果；新环境从用例起点重跑，失败清理可核查 |
| BD14 | 新业务用例只映射 build/健康 smoke | 显示业务观察缺口，不能生成对应断言通过结果 |
| BD15 | 受控新增测试试图删断言、跳过或修改固定脚本 | 测试评审/权限校验拒绝；原固定检查字节不变 |
| BD16 | 测试包改变但源码不变 | 旧批准与测试结果失效，重新评审、批准及执行 |
| BD17 | 用例正确版本，但运行镜像/迁移/数据集不符 | 版本门拒绝，不能借同一环境名或分支名通过 |
| BD18 | 旧 fixture 已完成、当前 live 只有产品稿 | 两者分别显示原事实，不能合并成业务交付成功 |
| BD19 | 发布回执为人工报告且缺构建关联 | 明示来源和缺口，不展示机器验证同版本发布 |
| BD20 | 全部必需旅程/异常及同版本证据齐全 | 才允许形成对应范围的业务验收通过；真实试点收益仍需实际观察 |

效果评估另行记录澄清重复率、确认规则丢失、业务缺陷漏检、人工补写/代操作次数、返工成本和真实试点收益。没有基线时不编造改善比例，也不以角色或文档数量衡量提升。
