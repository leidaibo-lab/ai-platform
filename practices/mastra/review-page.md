# 产品交接物审阅页

首版目标：产品负责人直接阅读 Workflow 生成的 Markdown 交接稿，围绕同一版本向只读助手提问，并提交人工决定。它是独立 Mastra 学习应用，不改变探索主线的 API、权限或数据契约。

## 页面与规则

本轮增加修订闭环：在阅读助手下方填写明确的“已确认结论”，可将当前聊天作为参考生成一份持久化修订提案。提案展示完整新稿与逐行增删差异，只有填写应用人并点击“应用并创建新轮次”才写入新 Run。新稿原样采用已预览正文，重新停在产品确认，不继承任何旧批准；原 Run、正文及决定保持历史。聊天是参考材料，只有明确填写的结论作为修订依据，不把助手建议自动转成已确认需求。

提案由单独的 Mastra 原生 Workflow 保存，可通过 URL `proposal` 参数在刷新后重开。应用动作按提案对应固定新 Run 标识，重复点击或响应丢失后重试返回同一新 Run；版本、模式与来源再次校验。正在运行的来源不能应用修订，旧稿处于待审或历史状态均可另起新版。旧待审轮次不会自动拒绝；需要时由负责人单独处理。

- 记录列表分页读取 `product-delivery` 的 Run，展示原始需求、时间和业务状态。空态引导到 Studio 创建流程，不制造演示数据。
- 正文保持已保存内容，显示真实模型提案或固定样例标签；可下载 Markdown、查看产品审阅记录。正文不可编辑，已结束或已进入下游的记录仍可阅读。
- 只有 `suspended` / `review-product` 且模型模式相同的 Run 可以操作。审阅人标签和意见均必填，沿用现有长度限制；标签不代表已认证用户。
- 确认前说明将生成开发提案；拒绝前说明结束本轮、不会修订当前稿。提交携带正在阅读的 hash，由服务端重新检查阶段、模式和版本，再调用现有恢复服务。
- 提交期间禁用重复操作。版本/状态变化返回冲突并刷新记录；网络失败保留输入，先刷新状态再决定是否重试，页面不自动重发批准。下游生成失败时区分产品决定已保存与后续步骤失败。
- 阅读助手使用当前 Run 的产品正文及版本，回答解释、覆盖与缺漏问题；没有编辑或审批工具。服务端取正文，浏览器不能覆盖上下文或注入系统角色/工具参数。切换 Run 或版本时重置本地对话；聊天不单独持久化，主动生成修订提案时将可见讨论作为参考随提案保存。助手回答不会直接修改正文或审阅意见。
- Markdown 不执行 HTML、脚本或外部图片；保留中文、表格、列表、代码和安全链接阅读能力。

## 技术边界与选型

- React + Vite 独立前端，AI SDK `useChat`/`DefaultChatTransport` 处理助手流；shadcn/ui AI Elements Message 模式与 Vercel AI Elements Artifact 组件按源代码方式采用，Markdown 使用 Streamdown。组件来源随代码保留。
- Mastra `registerApiRoute` 注册 `/review-api`，只返回页面所需字段；AI SDK 协议使用官方 `@mastra/ai-sdk` 的 `handleChatStream`，避免自研流协议。只读助手是独立用途的 Agent，不参与交付调度。
- LibSQL Workflow 快照仍是唯一交接与决定事实源；服务端复用当前 `deliveryStatus` / `reviewDelivery`，前端不维护审批数据库。开发代理统一同源 `/review-api`，服务仅本机监听，不提供公网或多用户权限承诺。
- 选择组合 UI 是因为 Studio 已证明适合调试，但无法满足业务阅读体验；纯静态 Markdown 缺审批闭环；自行编写模型流协议会重复 AI SDK/Mastra 已有能力。框架实践范围内的组合不代表探索主线采用。

本次自写范围是业务文档投影、页面与输入校验。HTTP Adapter 依赖 `DeliveryContext` 并复用交接服务，避免与应用装配形成循环依赖；`ProductReviewDocument` 是带可选正文的只读返回结构，确认请求必须绑定 64 位 SHA-256，正文和审阅事实始终归 Workflow。`Set` 仅隔离当前 HTTP 进程内的重复决定，不承担分布式锁。

适配器模式负责 HTTP 与原生服务/SDK 流的转换；React 只持有选中项、表单和易失问答，落实状态所有权与单一职责。复用原生恢复服务避免重复状态机；没有新增通用引擎、审批数据库或框架适配协议。实践贡献者维护页面、投影和回归；后续换 UI 可保留 Mastra 快照与现有 CLI。触发真实多人使用、跨实例部署或同轮修订时，需要重新评估身份、并发和版本规则。

AI Elements 按源码方式适配，Vercel Artifact 为 Apache-2.0，shadcn Message 为 MIT，完整归属与许可见 [web/THIRD_PARTY_NOTICES.md](./web/THIRD_PARTY_NOTICES.md)。AI SDK 历史消息由页面投影成纯文本再发送，排除步骤和供应商元数据；后端继续拒绝系统角色、工具内容和客户端模型配置。

修订复用产品 Agent 与现有产品 Skill，使用独立原生 `product-revision` Workflow 保存提案。新交付输入增加可选 `revision`，原来只传 `brief` 的调用和旧快照仍有效；有修订时产品生成节点直接采用已预览正文，后续角色同时收到当前批准稿与明确修订结论。来源、提案、应用人和结论随新 Run 保存，hash 也绑定修订来源。逐行比较采用成熟 `diff 9.0.0` 的 `diffLines`，不自写差异算法；与完整双栏相比便于定位大文档变更，仍提供完整新稿阅读，超时则退回完整正文。此依赖仅安装在实践前端。

## 本实践 API 契约

| 接口                                  | 行为                                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `GET /review-api/runs?page=0`         | 每页 20 条 Run 摘要及总数；仅提供需求、状态和时间                                                |
| `GET /review-api/runs/:runId`         | 产品正文/hash、需求、审阅记录、当前阶段、模型模式、能否审阅                                      |
| `POST /review-api/runs/:runId/review` | 接收 `artifactHash/decision/reviewer/comment`；产品角色由服务端固定，恢复到下一暂停点或终态      |
| `POST /review-api/runs/:runId/chat`   | 接收当前产品 `artifactHash` 和最多 20 条纯文本 user/assistant 消息；返回 AI SDK v7 UIMessage SSE |
| `POST /review-api/runs/:runId/revisions` | 接收 `artifactHash/confirmedDecisions/messages`，生成并保存修订提案；不创建新交付 |
| `GET /review-api/runs/:runId/revisions/:proposalId` | 从快照读取提案、原稿及明确结论，供刷新恢复比较 |
| `POST /review-api/runs/:runId/apply-revision` | 接收 `artifactHash/proposalId/appliedBy`，原样应用服务端提案到固定新 Run；不接受客户端正文 |

非法输入返回 400，记录不存在返回 404，过期版本/错误阶段/模式冲突或本进程正在处理返回 409，未知故障返回固定脱敏错误。读写响应不缓存。本机串行学习应用，不声称跨实例并发或生产级审批幂等已验证。

## 验收

正常：从真实快照阅读正文，助手流式回答且 hash/正文不变；批准在同一 Run 生成开发提案并关闭产品操作，拒绝后结束本轮。

异常：空列表、不存在记录、无产品稿、后续阶段、业务 rejected、生成失败、旧 hash、空审阅人/意见、重复/并发提交、网络断开和助手错误均有可观察反馈；过期/非法请求不能消耗产品暂停点。固定模型端到端与真实模型效果分别报告，不审批用户已有 Run 来做测试。
