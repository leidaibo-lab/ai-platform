# 应用实践集合

本集合承接框架原生应用实践：今天可以学习 Mastra，之后可以学习 pi 或其他项目。每个实践先按照该项目的官方方式建立应用，再与本仓库的探索实现比较，理解架构差异及其适用条件。

## 与探索方向的分工

| 维度 | 探索 | 应用实践 |
| --- | --- | --- |
| 主要问题 | 自己实现后，能否解释机制、边界和取舍 | 成熟项目怎样解决真实问题，有什么收益与代价 |
| 代码位置 | 当前 `src/`、`demo/`、`scripts/`、`experiments/` | `practices/<项目>/` |
| 实现方式 | 自有 Runtime 与已有成熟组件组合，保留探索记录 | 优先使用目标项目原生入口、Agent、工具、状态和执行机制 |
| 比较依据 | 源码、契约、测试和已记录的运行证据 | 官方设计、锁定版本、实际运行和场景验证证据 |
| 结果用途 | 理解原理、检验自己的设计 | 学会使用、辨别架构差异、识别适用场景 |

集合统一目录导航、业务目标、验收问题和记录方式；各实践保留自己的入口、依赖、存储和原生抽象。无需先把框架装进现有 Runtime，也不预建统一引擎、插件注册中心或框架 Adapter。

探索主线的唯一 Runtime、SQLite 事实源和 LiteLLM 出口是该实现的设计选择；它们是对照对象，不是原生实践的准入条件。模型连接采用目标项目支持的方式，配置和凭据只由服务端或本地进程持有。是否选用同一兼容网关作为实验变量，由各实践记录说明。

## 每个实践怎样推进

1. **理解原生架构**：读取官方指南，记录目标版本、核心概念、调用链和状态所有权；先回答该项目通常怎样使用。
2. **运行原生最小应用**：在独立目录安装并锁定依赖，保存启动、输入和实际结果；不先导入探索主线实现。
3. **完成业务场景**：逐项实现已选业务目标，保留目标项目原生机制。必须新增的业务逻辑单独说明；原生缺失和尚未验证分别记录。
4. **验证正常与异常路径**：记录可复跑命令、交付物版本、失败、重启、重复请求和人工介入的实际行为。
5. **比较并复盘**：说明双方责任分配有什么不同、各自收益与代价、哪些场景更合适，以及还缺什么证据。

原生入门、固定数据测试、真实模型效果和生产运行分别报告。学习应用可以持续演进，不要求先作出平台采用决策；决定将能力集成或迁移到探索主线时，再按[方案选型治理](../docs/solution-selection-governance.md)形成独立决策。

## 当前共同业务问题

以“产品准备需求 → 开发实现与质量确认 → 测试验证与用例确认 → 运维确认部署方案”为学习场景。业务目标相同，不要求不同项目使用同一套流程引擎、数据库或角色抽象，也不假定每个项目都原生覆盖所有阶段。

| 阶段 | 交付与人工责任 | 核对问题 |
| --- | --- | --- |
| 产品 | 需求、范围、验收标准；产品确认交接版本 | 下游拿到的是哪个版本，需求变化如何传播 |
| 开发 | 代码变更、检查与评审证据；开发确认代码质量 | 实际执行在哪里，模型声明与代码事实怎样区分 |
| 测试 | 需求—用例映射、执行报告和缺陷；测试确认用例与结果 | 测试是否真的执行，失败退回和覆盖缺口怎样表达 |
| 运维 | 环境要求、部署步骤、验证和回滚；运维确认方案可行 | 方案与代码/制品版本是否绑定，哪些前提尚未验证 |

该场景的当前目标到部署方案确认。实际发布需要另行明确授权和环境。验证可以先选择部分阶段，但必须写明覆盖范围；人工角色模拟不能写成真实权限验证，生成文档不能写成部署验证。

## 怎样判断架构差异的好坏

比较单元是一项具体设计在指定场景中的行为，不给框架作没有证据的整体优劣排名。

| 维度 | 双方分别需要回答的问题 |
| --- | --- |
| 核心抽象 | 用 Session/Run、Agent、Workflow、Task 或其他对象表达什么，组合关系是什么 |
| 执行与状态 | 谁推进任务，谁保存权威状态，进程退出后实际从哪里恢复 |
| 人工交接 | 谁能确认、确认哪个版本，退回、重复确认与变更怎样处理 |
| 工具与代码执行 | 谁拥有执行环境、工具授权、文件、网络和副作用边界 |
| 上下文与记忆 | 自动管理与显式控制各覆盖什么，数据可否查看、修改和迁移 |
| 可观测与验证 | 能否关联模型调用、实际工具结果、测试报告和人工决定 |
| 开发与部署 | 原生需要多少配置、业务补充代码和基础设施，升级与排障成本是什么 |

每个比较结论应包含：场景与版本、观察到的差异、对应证据、收益、代价和适用条件。结论标明来自文档、源码、确定性测试还是真实运行；未验证能力保留为未验证，不用其他组件的能力替它补齐结论。

## 依赖、配置与证据

- 每个实践独立管理依赖和 lockfile，不修改根目录依赖来强迫各框架共用 SDK 版本。
- 每个实践使用独立配置、端口、数据库和运行目录，不共享探索主线的业务数据或真实密钥文件；示例只放无密钥的配置样例。
- 新增可执行应用时先处理本目录的敏感配置、生成数据、依赖与构建输出忽略规则，再安装运行。
- README 写明确切运行版本、命令、可重现输入、结果与限制；可复用测试和脱敏报告按需放在该实践内，不先建立空目录或虚构通过状态。
- Mastra 已建立独立应用和可复跑回归，版本、启动方式、证据与限制见对应 README；pi 尚未建立本目录的原生应用。确定性验证不替代真实模型质量、工程执行或生产验收。
