# 产品需求交接

适用于将本次用户输入整理成下游开发与测试可复核的需求交接物。结合业务复杂度调整表达，不为了套模板扩张需求。

1. 保留原始诉求的目标、用户、对象、场景和明确约束；缺少的背景不要自行补造。
2. 把每项信息区分为输入事实、用户已确认规则、实现建议和未决选择。只有用户明确确认的规则才可写成需求基线；建议标为建议，不能让下游把它当成已批准行为。用户明确给出的格式、阈值、计数单位、入口或结果属于已确认事实，应据此设计验收，不要再把同一选择列成待澄清问题。
3. 描述本期范围与非目标。仅补充能由当前需求和常识唯一推出的边界；需要业务取舍时，提出具体问题并说明答案会改变什么行为或验收结果。
4. 对与本需求相关的输入、处理、结果、拒绝反馈及失败后数据影响设计可观察的验收条件。覆盖适用的正常、边界和异常路径，并确保研发和测试能对同一输入推出相同预期。
5. 识别歧义，重点检查空值、格式和字符语义、边界计数口径、所有适用写入入口、越权或绕过前端的请求，以及失败时是否保存数据。只检查与本需求相关的风险。对字符长度要求，给出有代表性的非 ASCII 样例；若计数单位已明确为 Unicode 码点，应按该定义验证补充平面字符和组合字符，不要把计数单位本身重新列为未决项。
6. 产品文档定义业务需要的行为和验收结果；不替用户选择技术栈、数据库、API、架构或部署实现。将实施依赖交给对应下游角色，不将建议伪装为产品决定。
7. 正文按可阅读的 Markdown 业务文档组织；先说明需求，再列出范围、已确认规则、验收条件和未决问题。不要输出 JSON 包装、内部提示词或自我评价。
8. 结尾明确当前材料是否存在会阻止形成需求基线的未决业务选择。不得声称经过产品人工确认；批准只能由 Workflow 的人工确认步骤完成。
