## 问题

当前产品角色能形成需求稿，独立开发 Workflow 已能按批准方案执行受限任务。任务只有角色、文件与依赖信息，缺少任务级验收/上下文/验证交接；自检通过后直接生成研发交付包，尚无独立只读代码评审。

此外，旧产品提案链在批准后继续生成开发、测试和运维提案。若只在旁边追加开发执行，会形成同一需求的两条下游路径，界面与证据含义不清。

目标是提高需求到代码的可追溯性、减少开工阻塞遗漏和交付遗漏，并通过同条件样本审查收益与新增成本。流程图更细和文档更多不算质量提升证据。

## 约束与非目标

- 沿用已锁定 Mastra 原生 Agent/Workflow/Store、受限工具和执行身份/检查点，不新增调度器或第二套审批状态。
- 已批准产品、方案、任务、源码和评审证据绑定版本；模型不能授予文件/命令权限或批准自身产物。
- 首版仍显式启动开发，要求已批准产品及项目 manifest；结束于研发交付，不建设独立测试或运维发布。
- 保留旧提案链、旧执行 Workflow 及历史暂停快照；新行为版本化，不将旧终态标为已通过新增评审。
- 本轮导入四个受治理的适配方法与 v2 运行代码，保留工作区原有恢复修复；不使用付费真实模型冒充质量验收。

## 淘汰条件

引入第二套任务/批准事实、模型直接放行、扩大可写范围或执行任意命令、覆盖旧快照、评审失败自动当作通过、没有来源锁而运行时拉取最新方法，均不接受。

## 决策

- 结论：**适配**。用户已授权运行修改；固定来源核验及隔离原生回归后接受工程接入，真实质量门禁保持独立。
- 方法基线：BMAD npm 发布包 `6.12.0`，元数据 gitHead 为 `05bfbd46d00766ec88eb9b42e76be2c575d64d7b`。11份源文件与该 commit raw 字节一致；不将 tag 对象或移动分支当 commit。发布包 SHA256 为 `ac05c93f0b3c4256bb4072e6e1ff181eaad6cc0a64a27a63893bfb2b0b64aed2`。
- 选择：少量上下文、任务交接、就绪和代码评审方法；原生 Mastra 版本化产品交接与开发执行。
- 实践拥有：批准/权限契约、结构数据、证据 hash、版本入口、预算和交付门。
- BMAD 提供：被选择的方法、模板和检查维度；Mastra 提供：执行、工具循环、步骤持久化、暂停恢复。
- 不新增 BMAD 状态机/状态文件，不全量复制其产品角色或整个 Skill 库；已比较 PM 的 intended-vs-implemented/code-review：评审正确性范围有交集，因此不向开发角色挂完整产品套件；BMAD 入口只承担冻结意图/任务规格、开工可实现性和逐发现证据处理。此次没有证明 BMAD 比已有方法更优，真实对照仍待验。

## 实施边界与计划

详见[融合设计](../../practices/mastra/bmad-workflow-integration.md)的节点表、契约、门禁、迁移和代码映射。

1. 固定上游资产、许可证、引用与散列。通用方法进入根 `.agents/skills/development/bmad-*`；当前实践 `product-pm` 的例外不自动扩展。同步根 Skill 索引及治理校验。
2. 新建 v2 契约与 `development-execution-v2`：上下文 → 架构/任务 → 就绪 → 批准 → 实现 → 检查 → 只读评审 → 交付。自检不再直接写 v2 交付终态。
3. 新建执行模式产品入口，复用四角色，在批准版本处结束；旧提案链保留。服务从 allowlist 原生 Workflow 读取真实批准，不接受客户端正文伪造来源。
4. CLI/服务按已保存 Workflow 版本定位并与权威输入核对；旧缺省版本只进旧流程，新旧 schema 和交付对象不能混用。
5. 完成隔离主路径和最高风险边界后评估正式接入；再做真实业务质量对照，页面启动开发另作后续切片。

新增数据为不可变 `ProjectContext/TaskPackage/ReadinessReport/CodeReviewReport/GateDecision` 与 v2 交付包；未到相应阶段时可空，交付前关键证据必须非空。方法版本、批准包和源码证据明确绑定，源码正常实现变化通过检查点推进，不与初始 baseline 永久比较。

采用原生 Workflow 组合、Agent 工厂和资产布局 Adapter；宿主确定性校验与模型语义评估分离，业务 I/O 与结构校验分离。复用现有权限/身份不变量保持 DRY，只引入本次可验证的字段和步骤保持 KISS；不建设泛化任务平台。

依赖和模型配置本轮不变；实现阶段优先复用已锁定版本。新步骤的恢复位置和预算必须明确，不能让只读评审故障重放已完成实现。跨库原子交接、跨实例 exactly-once 和运行中强杀恢复仍不承诺。

## 风险与退出路径

多次读取与评审增加成本；报告可能误报或造成重复澄清；上下游版本不一致可能误用旧批准。通过少量方法、任务级上下文、引用依据、版本绑定和有界预算控制。维护者负责资产升级差异、许可和回归，不自动追踪上游 HEAD。

退出时停止创建 v2 Run，保留结果和证据只读；新任务可使用旧入口。不得让已启动 v2 绕过新增门禁降级交付。发生严重误报、无质量收益、成本过高、上游变更或真实全栈需求超出现有执行范围时重评。

新增不可变上下文、原文行定位索引、TaskPackage、就绪/评审报告、发现处理记录、阶段检查点和交付证据。引用存在和任务/权限约束由宿主校验；语义仍由只读模型评估。自检通过不能交付，检查缺失、报告异常、严重未处理发现、旧批准和源码漂移均阻断。CONCERNS 先逐项证据裁决再批准；FAIL 返回产品澄清或人工终态。人工只能把有证据的误报记为 not-an-issue、将低/中严重性代码关注记为 defer；严重发现不能延期，完整性发现无风险接受通道。裁决是本地人工标签，不是自动证明发现不成立或真实账号认证。

实现问题按责任任务有界修复；架构阻塞重新准备上下文/任务/就绪并批准；`maxReworks` 不被重新规划重置。单角色临时模型故障最多2次调用，人工故障接续全Run最多1次，总调用上限72、单次Agent最多12步，每次输出/时间预算固定。就绪和评审故障在原phase续办，重开Store后不重放已完成实现。源码改变后重跑全部已登记检查和独立评审。产品澄清使用新批准版本和新目录关联旧Run，不继承旧批准。
