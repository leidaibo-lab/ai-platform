# ADR：采用统一 Team Loop 信封、返工 Port 与项目 Adapter 注册表

- 状态：接受
- 日期：2026-11-21
- 决策者：平台维护者（用户于 2026-11-21 确认“按建议实施”）
- 关联：`2026-11-19-three-layer-harness.md`、`2026-11-14-mastra-workflow-team-boundaries.md`

## 背景

产品、研发和测试已经分别形成可运行的 Mastra Workflow，但状态契约、返工交接和项目装配仍按单个团队或单个 Node 项目实现。测试团队直接调用研发内部返工函数，`node-test.v1` 的路径和命令也固化在项目装配与执行器中。这使“平台通用 Team Loop”只能复用流程形态，不能稳定复用团队边界和多技术栈能力。

## 决策驱动因素

- Mastra Workflow/Store 必须继续持有运行、暂停、审批和恢复事实。
- 团队专业状态不能被一个最低公分母 Schema 取代。
- 跨团队交接必须版本化、可验证，并保持来源证据与累计预算。
- 项目只能从服务端登记的固定 Adapter 与固定 Git commit 装配，浏览器不得提交路径、命令或 commit。
- 历史 Run 必须使用创建时的 Schema、工厂和项目绑定恢复。

## 比较方案

### 方案 A：保持团队间直接访问内部状态

改动最小，但测试会继续了解研发阶段、路由和内部字段；新增团队或技术栈会复制同类分支。无法形成稳定跨团队契约，拒绝。

### 方案 B：建立新的通用 Loop 状态机和持久层

可获得表面统一，但会与 Mastra Workflow/Store 重复保存运行、审批和恢复事实，形成双事实源；专业团队状态也会被迫迁移。违反既有架构约束，拒绝。

### 方案 C：统一信封与纯决策 Kernel，专业状态留在团队内（采用）

平台提供版本化 Team 信封、停止语义、返工请求 Port 和项目 Adapter 注册表。Kernel 只做确定性决策，不持有状态、不审批、不替代 `dountil`。团队 Workflow 继续拥有专业状态和策略；项目 Adapter 只暴露登记路径及固定执行计划。该方案能渐进迁移，并保持 Mastra 为唯一事实源。

## 决策

1. 新 Run 使用 `team-run-envelope.v1` 作为团队状态的版本化投影；专业状态仍由各团队 Schema 持有。
2. 跨团队返工使用 `rework-request.v1`。测试只能提交来源、目标、状态版本、来源散列、缺陷和证据引用；研发 Port 负责验证并生成新的研发状态。
3. `Team Loop Kernel` 仅提供终态、停止和下一动作的纯函数。实际循环仍由 Mastra Workflow 原生步骤、`dountil`、suspend/resume 和 Store 执行。
4. 项目装配使用服务端 Adapter 注册表。Adapter 负责 manifest Schema、候选路径、角色、检查展示和固定执行计划，不接受 manifest 中的任意命令。
5. 项目选择以服务端登记 ID 进入 Run，初始化时冻结项目 ID、origin、root、revision、Adapter ID 与 profile hash。历史 Run 不猜测迁移。
6. 首批 Adapter 为 `node-test.v1` 与 `python-unittest.v1`；后者提供第二个真实技术栈的固定 Python 编译和测试执行证据。引入 pytest 前需由受控运行镜像固定依赖版本，不依赖宿主偶然安装。

## 影响

- 正向：测试不再修改研发内部状态；团队停止语义可横向复用；项目路径与执行策略从通用层移出；新增技术栈有明确扩展点。
- 代价：项目选择、资产归属和执行入口必须携带 Run 冻结绑定；Adapter 需要独立契约测试。
- 风险：把信封误当持久状态、把命令开放给 manifest、或按当前注册表静默迁移旧 Run。恢复必须用 Store 冻结绑定校验当前登记值；项目缺失或绑定漂移时拒绝执行，不能默认选择首项。

## 验证

- 契约测试覆盖信封、Kernel、返工 Port 的版本、散列、证据和预算拒绝。
- Adapter 契约测试使用两个临时 Git 仓库，验证固定版本装配、协作规则、写入边界与真实检查。
- 主 Workflow 测试验证 Run 冻结绑定，恢复时注册表漂移被拒绝。
- OpenSpec 严格校验、类型检查、目标回归和全量测试共同作为接受证据。

## 实施进度（2026-11-21）

研发与测试已接入公共信封和返工 Port。固定 argv 生成迁入 Adapter；新 `adapter-profile.v2` 绑定计划模板、解释器版本、路径和可执行文件摘要，Python 检查前后复核程序摘要。旧 profile 按原 manifest 散列恢复，不伪称具有新运行时保证。

Run 级注册表及工作台选择已接入产品上下文、开发候选、归档、项目同步设置、后继与 MR。配置不再通过修改共享对象切换项目；原生入口预检和外层步骤校验保护 Store 冻结绑定，异步作用域只携带已验证配置和根 Run 来源。资产文件及 bundle 必须显式选择项目，历史单项目同步设置保持原路径，避免已禁用策略被重置。

验证入口为 `tests/run-project-routing.test.ts`：两个真实临时 Git 项目的 Node/Python 并发流程、Store 关闭重开、注册表逆序、资产/候选/归档归属及原生错绑拒绝；MR 外部端口使用受控替身，不执行真实推送。

标准库及动态库内容尚未作为完整环境镜像冻结，不能声称环境可跨机器复现。项目注册表不是租户权限系统，现有本机工作台的认证边界不变。

恢复回归同时发现平台修复通知的旧暂停竞态：不同事件对同一故障通知时，普通 `resume()` 可能等待首个执行结束，再错误认领下一人工暂停。修复使用现有 Mastra Store 的 `updateWorkflowState` 原子认领，核对返回快照未发生暂停版本变化后委托 `resumeClaimed`。实际消费事件与响应状态按 Store 回执匹配，不建立另一套通知或恢复事实源。

这一薄适配依赖当前固定 `@mastra/core@1.81.0` 的 Run 内部入口和 `resumeClaimed` 行为；依赖升级必须重跑原生入口拒绝、并发创建、跨进程平台修复与嵌套恢复测试。进程内同 ID 首次启动互斥仅覆盖当前实例，不承诺跨进程原生首次启动的原子防重。
