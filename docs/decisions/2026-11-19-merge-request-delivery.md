# 将产研主线交付收敛到合并请求

状态为接受。用户已确认当前交付阶段截止于向 `main` 提交 MR。此决策调整[试点部署生命周期](./2026-11-07-mastra-full-delivery-lifecycle.md)在默认流程中的终点，沿用[三层 Harness 职责](./2026-11-19-three-layer-harness.md)。

## 取舍

采用 GitHub 的拉取请求作为当前仓库的 MR 实现，使用 Git 和 `gh api` 适配。沿用 Run 分支和版本化 QA，主 Workflow 在交付团队拿到经核对的远端回执后结束。Mastra Store 保存交付事实，GitHub 持有实际请求。由部署维护者准备更细粒度凭据和其他托管平台时，再扩展适配。

现有人工发布回执路径保留供旧部署 Run 使用。继续使用人工回填 MR 会使版本确认依赖输入，因此当前选用服务端读取或创建真实请求。自动合并、CI/CD、部署和回滚归后续建设。

## 实施与验收

- 主编排默认从测试进入交付，校验 QA、正式规格和候选文件。Git 写入限制为授权的 Run 分支和候选路径。
- 创建前查询现有 MR。失败保留原生暂停点，恢复时核对远端分支和请求，旧版回执无法放行。
- 保留历史生命周期状态和试点部署 Workflow 装配。已暂停在部署节点的旧 Run 可在原部署图恢复。默认图用于新 Run。
- 用 fixture 验证正常入口和终态，用隔离 Git 仓库和替代的 GitHub API 验证候选推送、回执匹配及重试。真实远端交付应使用获授权的测试仓库。
