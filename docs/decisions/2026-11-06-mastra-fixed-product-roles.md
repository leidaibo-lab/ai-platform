## 问题

现有产品阶段只有一次产品 Agent 生成及一个人工暂停点，无法分别观察需求理解、规则闭环和文档表达的工作。拒绝后结束本轮，返工反馈需要人工再次整理。用户确认先固定职责和路径，验证分工是否减少遗漏、缩短人工审阅时间；当前没有真实质量提升证据。

## 约束与非目标

- 复用已锁定 `@mastra/core 1.81.0`、`@mastra/libsql 1.28.0`，不升级或增加依赖。
- 四个角色均为原生 Agent，能在有限步数内使用已注册工具和 Skill；不进一步拆分下级 Agent，不开放任意文件、网络、命令或审批工具。
- 状态、步骤输出和暂停恢复继续由 Mastra/LibSQL 持有；不建设调度器、审批数据库或跨实例锁。
- 人工批准必须绑定当前产品 hash，模型不能放行到开发。
- 保留既有拒绝终止和修订预览的语义，新增明确的“退回修改”操作。
- 旧暂停点及文档可回读；不修改用户现有 Run，历史兼容验证限于隔离数据库中的旧单产品步骤暂停快照。
- 本次不解决动态角色、生产部署、实际工程执行、真实身份、Agent 长期记忆，以及真实产品质量的量化验收。

## 候选方案

| 候选 | 路线 | 优势 | 缺口或风险 | 证据 |
| --- | --- | --- | --- | --- |
| Mastra 原生子 Workflow + 固定 Agent | 成熟框架原生组合 | 复用当前 Agent、步骤持久化和人工关口；角色产物可独立检查 | 业务角色、反馈与版本关系仍由实践定义 | 官方 Workflows overview/control-flow；本地锁定包的 `createWorkflow`/`then` 类型声明；现有暂停恢复回归 |
| Agent 自主规划和动态委派 | 动态编排候选 | 能针对开放问题改变执行路径 | 当前先验证固定分工，动态角色和路径会增加质量归因变量 | 用户明确选择固定角色；官方 Agents overview 将 Agent 推理与工具选择和 Workflow 编排分开说明 |
| 手写角色循环与执行状态存储 | 最小自研 | 可精确控制所有细节 | 重复实现当前框架的步骤、快照和恢复，增加维护面 | 本地已有原生 Workflow、LibSQLStore 和共享审阅服务 |

这是原生实践内的组织决策，未进行跨框架平台选型；不以它推导 Mastra 平台采用结论。

## 淘汰条件

绕过人工批准、覆盖旧文档、开放模型任意修改角色/权限、引入第二套状态事实源，均不接受。

## 关键验证

实施前已核对：原生 Workflow 可作为步骤组合，Agent 支持有限步数工具调用，现有 `review-product` 使用原生暂停恢复并绑定 hash。实施后必须验证角色顺序与产物、工具事实、返工后重新等待产品批准、旧 hash 拒绝、返工重试及跨进程恢复。实际结果追加于文末。

## 决策

- 结论：采用 Mastra 原生子 Workflow，适配产品角色与返工业务契约。
- 产品子流程：总产品 → 需求梳理 → 产品闭环 → 产品写作；每个角色交付有序产物和工具使用摘要。
- 首版返工固定从总产品和需求梳理重新走完整子流程，不由模型跳过角色；总产品定位问题并指导处理。
- 返工采用保留来源的独立 Run，沿用当前修订新轮次约定。旧轮次保存反馈与终态，新轮次绑定来源 Run、hash、原稿和意见，并重新等待人工批准；不承诺同一 Run 原地循环。
- 返工最多三次；达到上限后保留人工审阅点，允许批准或终止，需要负责人重新梳理后另起需求。
- 原有“拒绝”仍终止；新增“退回修改”才触发返工。批准照常推进开发。
- 应用已预览修订稿仍原样采用，避免用户比较后再次生成不同正文；该路径不伪造四角色执行记录。
- 框架负责执行、工具循环、快照和恢复；实践拥有角色提示、交接数据、版本散列、反馈来源和审阅投影。

## 未采用方案及原因

动态委派增加归因变量，等稳定场景反复需要现有角色以外的专业能力时再评估。手写执行引擎重复现有能力，只有原生组合经验证无法满足明确场景时再重评。

## 实施边界与计划

- 修改 `practices/mastra/src/mastra/agents/`，增加三个产品角色并明确既有产品 Agent 的写作职责；沿用原生 Skill 工具和只读 `practiceInfo`。
- 新增产品数据契约和子 Workflow；外层保留 `draft-product`、`review-product` 等步骤标识，维持人工关口和既有文档投影。
- 共享交接服务新增返工动作和固定新 Run 标识；相同已保存决定重试只回读同一后继。只支持单机串行使用，HTTP 沿用进程内互斥。
- 产品稿和中间产物不可变返回，审批不继承；返工来源保存在 Workflow 输入，历史由来源链接追溯。
- 页面增加退回入口、返工来源和角色产物阅读，客户端不提交正文、角色编排或工具选项。
- 工厂模式复用 Agent 配置，原生复合 Workflow 表达职责组合；I/O、输入校验和投影分层，不引入通用 Agent 框架。
- 配置和依赖不变。旧数据结构的新字段可选，旧 root 人工步骤保持；产品新能力主要通过新 Run 体验。

## 风险与退出路径

角色分工可能重复或传递时丢失信息，因此各角色同时接收原始诉求、已有角色产物与返工原稿；写作不能自行确定业务规则。多次模型调用增加成本，使用有限步数和返工上限。运行中生成失败不自动重试模型，也不自动批准。跨 Run 建立返工不是事务内 exactly-once，恢复仅回读稳定新 Run，不宣称跨实例竞争或崩溃恢复通过。

实践维护者负责业务契约、页面和回归；保留原生 Markdown/hash/来源数据可导出，回退前停止新建返工并保留历史只读入口。出现动态职责、复杂图内回退、跨实例、长期任务或真实质量收益不足时重评。
