# C1 链路深挖问题清单

## 这份清单要解决什么问题？

C1 已经形成可运行的功能基线，但“系统能够运行”不等于团队真正掌握了这条链路。只知道项目用了 Ant Design X、SQLite、AI SDK、LiteLLM、OpenTelemetry、Phoenix 和 Open-Meteo，仍然无法回答下面这些架构问题：

- 当约束变化时，现有方案还成立吗？
- 第三方能力解决了哪一段通用问题，平台仍然必须拥有哪些业务语义？
- 为什么采用当前方案，而不是另一个成熟方案或自己实现？
- 哪些失败允许自动恢复，哪些失败会造成重复输出或重复副作用？
- 哪些测试只证明适配正确，哪些证据才能证明真实业务效果？

这份清单不要求背诵结论，而是要求沿真实链路建立可解释的决策能力。

## 回答每一组问题时，是否都覆盖了八个维度？

对任何一项 C1 能力，都应先按下面顺序回答，而不是从“准备使用哪个库”开始：

1. **问题是什么？** 当前用户损耗、业务风险或工程失败是什么？如果不建设会发生什么？
2. **约束是什么？** 数据、安全、部署、时延、成本、兼容和团队维护能力有哪些硬边界？
3. **候选有哪些？** 是否覆盖成熟一体化、轻量可组合和最小自研三类路线？
4. **淘汰条件是什么？** 哪个条件一旦不满足，就不应该继续比较功能多少？
5. **为什么采用、适配或自研？** 当前选择解决了什么，为什么没有选择另外两类？
6. **平台拥有什么？** 哪些契约、数据和治理语义不能交给第三方成为事实源？
7. **证据是什么？** 官方资料、源码、协议测试、异常回归、真实模型或运行态证据分别证明了什么？
8. **何时重新评估？** 规模、场景、风险或上游版本发生什么变化时，当前结论会失效？

如果回答只是“这个框架支持该功能”“业内都这样做”或“自己实现更可控”，说明还没有完成选型分析。

## 能否先说清 C1 到底解决什么问题？

- C1 的业务结果是“模型返回一段文字”，还是“用户可以围绕同一会话持续提问、纠正、取消、恢复并得到确定状态”？
- 为什么连续对话不能简化成浏览器把全部历史拼成 Prompt？
- 模型、渠道、Runtime、连接器和模型网关各自知道什么，又明确不应该知道什么？
- 为什么所有业务模型请求必须经过 Agent Runtime，而 `scripts/test-chat.sh` 只能是模型连通性诊断链？
- C1 中哪些是权威事实，哪些是派生视图，哪些只是网络中的瞬时状态？
- 如果删掉 Runtime、Store、Context Planner、GatewayClient 或 ChainTrace 中任意一层，具体会失去什么确定性？
- C1 功能基线完成与完整运行态验收完成有什么区别？为什么当前允许前者收口、后者按触发条件延期？

## 渠道为什么采用 Ant Design X，而不是继续自研或迁移整套 AI SDK UI？

### 先追问问题与边界

- 当前渠道缺的是一个输入框，还是会话列表、附件、流式 Markdown、操作菜单、取消、引用、移动端和可访问性的一整套通用交互？
- 哪些页面状态只影响即时体验，哪些状态必须回到 Runtime 和 SQLite 收口？
- 为什么关闭浏览器连接不能自动解释为用户取消？
- 为什么 UI 可以乐观展示文本增量，却不能自行宣称 Run 已经 completed？
- 为什么模型原始思维链不应该成为渠道展示数据？渠道能展示的真实阶段证据有哪些？

### 再追问方案选择

- Ant Design X、AI Elements + AI SDK UI、继续扩展静态页面分别会替换哪些现有边界？
- 为什么 Ant Design X 适合企业工作台，而 AI SDK UI 的消息协议当前不能直接替换已有 JSON Run、POST SSE 和事实事件流？
- 为什么采用 UI 组件不等于采用它的 Runtime 或数据协议？Adapter 在这里隔离了什么？
- 为什么通用输入、消息、Markdown 和可访问性交给成熟组件，而 Run 状态、取消、引用和错误分类仍由平台定义？
- 包体、版本兼容、移动端和可访问性用什么证据验收，而不是只看一张截图？
- 出现多个 Web 产品统一要求 AI SDK UI 协议时，什么实验结果才足以触发重评？

## 为什么 Conversation、Message 和 Run 必须由平台拥有？

- Conversation、Message、Run 分别描述长期资源、不可变事实和一次执行，为什么不能合成一个对象？
- `conversationId`、`messageId`、`clientMessageId`、`requestId`、`runId` 和 `chainTraceId` 分别防止哪类混淆？
- 为什么 `requestId` 的幂等与 `clientMessageId` 的消息去重不能共用一个唯一约束？
- 为什么模型调用前必须先提交用户消息和 Run？先调用模型再落库会产生哪些不确定窗口？
- 为什么重试、重新生成和继续生成要创建新 Run，并保留 `sourceRunId + recoveryMode`，而不是覆盖原 Run？
- 为什么 Session/Run 契约不直接交给 AI SDK Agent Session、LangGraph thread 或浏览器状态管理？
- 哪些状态转换必须在同一个 SQLite 事务中完成？事务失败后允许留下哪些事实，绝不能留下哪些半状态？
- 如果未来迁移到 PostgreSQL 或独立 Runtime 服务，哪些领域字段和不变量必须保持不变？

## 为什么当前使用 SQLite，它的适用边界在哪里？

- 当前单进程、本地 Demo 和轻量部署为什么适合 SQLite，而不是一开始就引入 PostgreSQL、Redis 和消息队列？
- WAL、`busy_timeout`、唯一约束和事务分别解决什么问题？它们不能解决什么问题？
- 为什么浏览器缓存、Trace 后端和 LiteLLM 都不能成为 Conversation 事实源？
- 当前按 `conversationId` 的进程内串行解决了什么顺序问题？为什么它不是分布式锁？
- 两个 Runtime 实例同时处理同一会话时，现有 Coordinator 会失效在哪里？
- 出现哪些信号后才应该迁移：多人共享、跨主机、独立扩缩容、数据保留、备份恢复还是团队所有权？
- 迁移数据库时，如何证明幂等、顺序、引用、记忆版本和事件游标没有发生行为漂移？

## Context Planner 为什么不能等同于“拼历史消息”？

- 模型上下文窗口、平台输入预算、预留输出 Token 和安全余量分别是什么？
- 系统规则、当前输入、显式引用、active 记忆、Episode 和最近消息为什么具有不同优先级？
- 为什么候选应该完整入选或带原因排除，而不是从字符串中间截断？
- 高水位、低水位和硬水位分别控制后台压缩、目标窗口和同步门禁的什么时机？
- 为什么 Token 越少不一定越好，全部历史越完整也不一定越好？
- Context Manifest 为什么只记录选择证据和 Token 分段，而不复制 Prompt 正文？
- 当前轻量相关性排序在哪些场景会失效？需要什么基准才能引入 embedding、rerank 或外部检索能力？
- 如果第三方 Context Engine 能做召回和压缩，平台仍需要保留哪些预算、权限、来源和排除原因契约？

## 结构化记忆为什么部分自研、又为什么不能继续无限扩展？

- 原始消息、MemoryDelta、active/superseded 事实、Episode 和本轮上下文分别是什么？
- 用户纠正 RabbitMQ 为 Kafka 时，为什么旧消息必须保留、旧事实必须失效、新事实必须带来源？
- `memoryVersion` 乐观锁防止什么覆盖问题？为什么长时间模型提取不能持有数据库事务？
- 目标、约束、偏好、事实、决策和任务这些语义为什么属于平台，而不是第三方 Memory Provider？
- 记忆提取、向量索引、召回和排序为什么可以被外部能力替换？这与数据所有权是否冲突？
- Mem0、Letta、Supermemory、Hindsight、LangGraph Store 与当前实现应该如何使用同一 fixture 比较？
- 除了召回准确率，还应比较旧事实泄漏、实体隔离、来源有效、Token、延迟、成本、驻留和可导出性中的哪些指标？
- 什么结果才允许迁移某个提取或检索环节，而不是因为第三方功能更多就替换全部记忆模型？

## 为什么模型主链需要 GatewayClient、AI SDK 和 LiteLLM 三层？

- GatewayClient、AI SDK、LiteLLM 和上游 Provider 分别解决哪类问题？是否存在职责重复？
- 为什么 GatewayClient 是 Runtime Port，而 AI SDK 和 LiteLLM 都不能成为并列业务入口？
- AI SDK 帮助处理模型消息、流、工具和结构化输出后，平台还必须自己处理哪些错误、身份、事实和交付语义？
- LiteLLM 收口模型别名、密钥、路由和配额后，为什么不能保存业务会话、执行工具或决定上下文？
- 与 Vercel AI Gateway、直接调用 Provider SDK、OpenAI Agents SDK 或再建一套 Provider Registry 相比，当前组合的硬约束和退出路径是什么？
- 为什么浏览器只能看模型别名，不能获得真实上游模型名、Provider 账户或密钥？
- `/v1/models` 证明的是当前 key 可见的目录，为什么不能证明每个模型此刻都能成功生成？
- 为什么 LiteLLM、AI SDK、Zod 等依赖要固定版本或 digest？升级时必须重跑哪些协议和行为回归？

## 为什么工具型对话使用 ToolLoopAgent，其他调用仍保留 Core 函数？

- 工具循环真正包含哪些通用能力：模型选工具、schema 校验、执行、结果回填、停止条件、流式和错误传播？
- 为什么这些通用循环交给 AI SDK，而 Tool Registry、权限、ToolResult、幂等和审计仍由 Runtime 拥有？
- `ToolLoopAgent` 的 `prepareCall`、`prepareStep`、`runtimeContext` 和 `toolsContext` 分别解决什么动态装配问题？
- 为什么纯文本工具对话适合复用 Agent，而 MemoryDelta 等动态 `Output.object` 任务仍走 `generateText` / `streamText`？
- 为什么首步确定性天气路由不能只依赖 Prompt 或模型自觉？后续步骤为什么必须恢复 `auto`？
- 与自研循环、LangGraph、Mastra 和 OpenAI Agents SDK 相比，当前只有一个有界只读工具时为什么选择 AI SDK？
- 出现复杂分支、人工暂停、多 Agent handoff 或持久 checkpoint 时，哪些证据会使 ToolLoopAgent 不再足够？

## 为什么首个真实 Connector 选择天气和 Open-Meteo？

- 第一个工具的目标是证明“天气功能”，还是证明选择、校验、执行、回填、来源、失败和审计的最小闭环？
- 为什么首个工具必须无副作用、输入简单、结果可验证，并且不能接受模型提供的任意 URL？
- Open-Meteo、带密钥商业天气服务、通用 Web Search 和模拟工具分别有什么验证价值与治理成本？
- 为什么通用搜索不是更好的第一个工具？网页提示注入、来源质量和非结构化结果会干扰哪些核心假设？
- `get_weather` 的输入 schema、地点消歧、today/tomorrow 边界、超时、来源和观测时间应该由谁校验？
- 工具失败为什么要形成安全 ToolResult，而不能直接抛成“模型调用失败”？
- 真实天气只属于当前 Run，为什么不应自动写入长期记忆？
- 从天气扩展到企业业务数据时，还缺少哪些身份、权限、查询口径、数据版本和字段脱敏能力？

## ToolResult 为什么是事实，工具后模型失败为什么不能重放整段循环？

- 模型生成 tool call 与平台真正执行 Connector 有什么区别？谁对外部副作用负责？

- `outputStarted` 与 `retryBoundaryCrossed` 分别表示用户交付边界和外部执行边界，为什么不能只保留一个布尔值？
- 工具完成但最终总结失败时，为什么恢复输入必须重新从 SQLite 读取，而不能依赖 Agent 内存中的 step？
- 为什么恢复请求使用 AI SDK 结构化 `tool-call` / `tool-result` ModelMessage，而不是把 JSON 拼成普通 Prompt？
- 为什么恢复调用不能携带 ToolSet、`toolsContext` 或强制工具路由？
- 为什么只有 completed ToolResult、原错误以 `retry-boundary-crossed` 停止且尚未交付正文时才能自动恢复？
- 恢复成功后为什么仍然只允许一条助手消息？恢复再次失败时为什么要保留原失败和恢复失败两段 resilience？
- 当前恢复为什么只适用于单 Run，不等于跨进程工作流恢复？什么条件会触发 LangGraph 或 Temporal 评估？

## 为什么模型重试由 Runtime 统一管理？

- 网络超时、408、429、500、502、503、504、参数错误、鉴权失败和未知 SDK 异常分别是否可重试？依据是什么？
- `maxAttempts=3` 是三次重试还是包含首次调用的三次尝试？如何避免配置语义误读？
- 为什么整个 Run 共享绝对截止时间，而不是每次模型尝试重新获得完整超时？
- 退避、随机抖动和 `Retry-After` 分别解决什么问题？何时剩余时间已经不足以继续退避？
- 为什么 AI SDK `maxRetries` 保持为 0？如果 Runtime、AI SDK 和 LiteLLM 同时重试，请求数量最坏会怎样相乘？
- 为什么首个有效文本之前可以替换失败尝试，开始输出后却不能静默重生成？
- 用户显式取消为什么必须中止当前请求、退避和后续尝试？浏览器断连为什么不能做同样处理？
- 当前 RetryExecutor 为什么不是工作流引擎？它明确不应该增加哪些 lease、timer、补偿和跨实例能力？

## 为什么同时保留 JSON Run、POST SSE 和事实事件流？

- 正常完成、显式取消、模型失败、浏览器断连和幂等重放分别应该产生什么终止事件与持久化结果？
- 为什么已输出后的失败不能通过 SSE 自动拼接第二次生成？
- WebSocket、AI SDK UI Stream、Token checkpoint 和服务端事件流各自适合什么场景？当前为什么没有采用？
- 当多个正式渠道需要统一流协议时，Adapter 保留哪些 Run 事实语义才能安全迁移？

## 为什么 ChainTrace 采用 OpenTelemetry 和 Phoenix，而不是自己做日志平台？

- 普通日志无法回答哪些跨阶段、跨尝试和耗时归因问题？
- `requestId + conversationId + runId` 为什么要同时进入安全 Trace 属性？幂等重放时业务 Chain ID 与 OTel trace ID 应怎样变化？
- 为什么采用 AI SDK Telemetry + 项目 `ChainTracer` Port + OTLP，而不是直接依赖某个观测厂商私有 SDK？
- Langfuse、Phoenix 和自研 Trace 后端比较时，查询、隐私、部署、权限、保留、升级回滚和总拥有成本分别如何验证？
- 为什么最终选择 Phoenix？哪些能力属于 Phoenix，哪些身份映射、阶段命名、脱敏和采样仍属于平台？
- 为什么 `recordInputs=false`、`recordOutputs=false`？不记录正文后如何保留足够排障证据？
- 为什么 Trace 只能是旁路，不能成为 Conversation、Run、Message、Memory 或 ToolResult 的事实源？
- 为什么当前默认关闭正式导出？进入多人共享、准生产或出现日志无法定位的问题时，要恢复哪些运行态验收？

## 为什么确定性回归不能替代真实模型评测？

- 脚本模型和 fake LiteLLM 可以稳定证明哪些 Runtime、协议和状态行为？它们绝对不能证明什么？
- 真实模型评测为什么必须固定 fixture、Prompt、模型别名、实际模型、采样参数、输出上限和时间？
- 准确度为什么不能只看一个正确案例？最新纠正、旧事实泄漏、实体隔离、任务状态和来源有效分别如何计量？
- 实时性为什么要拆成接入、排队、Planner、首增量、模型完成、持久化和交付，而不是只看总耗时？
- 稳定性为什么关注确定状态和可恢复性，而不是要求系统永不失败？
- Token 合理性为什么要同时报告分段预算、实际 usage、排除原因、费用和质量？
- 样本少于 30 时为什么只报告观察结果？什么统计口径才足以形成基线？
- 第三方组件、模型或策略升级后，哪些确定性测试必须先过，哪些真实评测必须重新执行？

## 安全与权限问题是否在每一段都被问到？

- 浏览器、Runtime、LiteLLM、Connector、Provider 和 Phoenix 分别持有哪些凭据？哪一层绝不能接触真实 key？
- 用户正文、附件 URL、工具输入、ToolResult、原始错误和 Trace 属性分别需要怎样的最小化与脱敏？
- 为什么模型不能提交任意 URL、代码或未注册工具？Tool Registry 的 allowlist 防住了什么？
- 当前本地身份占位与正式租户/用户鉴权之间还有多大差距？哪些能力不能因为 Demo 可用就宣称安全完成？
- 会话引用、未来文档片段和业务记录为什么需要不同的所有权、版本、时效和权限校验？
- 工具结果中的外部内容可能包含提示注入时，平台、模型提示和输出校验分别需要做什么？
- 数据驻留、Provider 保留策略、工具第三方处理和 Trace 正文采集是否被分开评估？
- 进入写操作前，权限、预览、人工确认、业务幂等、结果回读和不确定状态是否全部有稳定契约？

## 如何证明自己已经深挖，而不是只读完了文档？

### 能否为每个能力产出一张决策卡？

每张决策卡至少回答：

```text
当前问题 -> 硬约束 -> 三类候选 -> 淘汰条件
-> 最终选择 -> 未采用原因 -> 平台所有权
-> 主路径证据 -> 最高风险异常证据 -> 剩余边界 -> 重评条件
```

### 能否画出三张不同目的的图？

- 业务主链图：谁调用谁，模型请求为什么只能经过 Runtime。
- 数据所有权图：Conversation、Message、Run、Memory、ToolResult、Trace 分别归谁。
- 失败与恢复图：输入、排队、规划、模型、工具、交付和存储失败后是否重试、恢复或终止。

### 能否不用产品名回答架构题？

把所有第三方名称遮住后，是否仍能解释：

- 为什么需要模型调用适配层和模型网关？
- 为什么需要服务端事实源、幂等 Run 和上下文规划？
- 为什么工具循环可以复用成熟引擎，但工具权限和结果事实必须平台拥有？
- 为什么可观测可以采用成熟后端，但业务 ID、阶段语义和脱敏规则不能外包？
- 为什么当前不需要工作流引擎，什么变化出现后又必须重新评估？

### 能否用异常案例反推选型是否成立？

至少能够逐一回答：

1. 同一请求响应丢失后重发，会不会重复计费和写消息？
2. 模型首增量前返回 429 与首增量后断流，处理为什么不同？
3. Connector 已完成后模型返回 503，为什么不能重放 Agent，怎样恢复总结？
4. 恢复调用再次失败，用户、Run、ToolResult 和 resilience 分别是什么状态？
5. 浏览器断线、用户取消和 Runtime 进程崩溃，当前分别能恢复到什么程度？
6. Phoenix 不可用时，为什么 Run 仍然必须正常完成或失败？
7. 100 轮确定性回归通过后，为什么仍不能宣布真实模型准确率达标？
8. 新增一个写工具时，为什么不能直接复用天气工具的自动执行策略？

## 最终是否能够给出这样的结论？

真正掌握 C1，不是记住“项目用了哪些第三方”，而是能够说明：

- 通用能力为什么优先采用成熟生态，减少重复实现和长期追赶成本。
- 平台为什么仍然必须拥有业务事实、身份权限、稳定契约、失败语义和验收证据。
- 当前每个选择建立在哪些约束和验证上，而不是因为某个框架功能更多。
- 当前明确没有实现什么，哪些变化会触发方案重评。

只有当团队能够对这些问题给出基于代码、契约、决策记录和测试的答案，C1 才真正从“完成了一项功能”变成可复用、可演进的工程能力。
