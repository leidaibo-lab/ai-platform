# C1 对话链路深入理解指南

## 这份指南解决什么问题

C1 是“连续对话问答”场景。它处理的不是一次孤立的模型调用，而是用户围绕同一个会话持续提问、补充条件、纠正旧事实、取消回答并继续追问的完整过程。

理解 C1，不要求先读懂项目源码，也不要求先学习模型训练原理。真正需要理解的是：一条用户消息如何被可靠地接收，如何与历史事实组成这一轮上下文，如何调用模型，如何把结果逐步交付给用户，以及系统如何证明整个过程准确、实时、稳定且 Token 使用合理。

读完后，应当能够用自己的话回答下面六个问题：

1. 为什么 C1 不是“把历史消息拼成 Prompt，再调用一次模型”？
2. 为什么浏览器、Agent Runtime、模型网关和模型必须分层？
3. 为什么原始消息、结构化记忆和本轮上下文是三种不同的数据？
4. 为什么有些失败可以重试，有些失败绝对不能自动重试？
5. 为什么用户关闭浏览器不等于取消模型生成？
6. 怎样证明 C1 真的可用，而不只是“模型返回了一段文字”？

## 一句话认识 C1

C1 是一套把“当前输入”转化为“可持续对话结果”的在线执行系统：

```text
接收当前输入
  -> 建立稳定身份
  -> 保存会话事实
  -> 选择本轮上下文
  -> 调用模型
  -> 流式交付结果
  -> 保存最终事实
  -> 更新长期记忆
  -> 记录链路证据
  -> 通过评测判断质量
```

模型只负责根据本轮输入上下文生成候选回答。会话属于谁、消息是否重复、历史事实是否已经被纠正、哪些内容应该进入上下文、失败后能否重试、回答是否已经交付、最终状态如何保存，这些都不是模型能够独立解决的问题，而是 Agent Runtime 的职责。

因此，C1 的核心不是“模型能力”，而是“模型周围的状态管理与执行治理”。

## 用一个案例贯穿整条链路

假设用户在同一个会话中进行了三轮交流：

```text
第 1 轮：当前项目使用 RabbitMQ。
第 2 轮：更正一下，当前项目使用 Kafka，因为需要事件回放。
第 3 轮：我们为什么选择当前的消息队列？
```

第三轮看似只是普通问答，系统实际上必须同时做到：

- 知道三轮输入属于同一个会话。
- 保留第一轮原始消息，不能因为纠正而篡改历史。
- 知道第二轮已经取代第一轮中的旧事实。
- 不把其他项目仍在使用 RabbitMQ 的信息混入当前项目。
- 在有限 Token 预算内优先装入最新有效事实和纠正原因。
- 如果请求被浏览器重复提交，不能重复保存消息或调用模型。
- 如果模型临时限流，应在总时间预算内进行受控重试。
- 如果模型已经输出“我们选择”，随后连接失败，不能偷偷重新生成另一版并拼在后面。
- 保存最终回答、实际模型、Token 用量和上下文选择证据。
- 能够通过一条 ChainTrace 看出时间花在了排队、规划、模型还是交付阶段。

只要其中任何一项没有确定行为，这条链路就还不能被称为稳定的连续对话链路。

## 先理解参与者，而不是技术名词

### 渠道与体验层

渠道是用户看到和操作的地方，当前是浏览器 Demo，未来也可以是 IM、IDE 或业务系统。

渠道负责：

- 收集当前输入和附件。
- 展示会话、消息和生成状态。
- 为一次提交生成客户端标识。
- 消费流式文本并增量渲染。
- 发起显式取消、引用和恢复操作。

渠道不负责：

- 保存权威会话历史。
- 自己总结历史并把总结当作事实。
- 判断一次 Run 最终是否真正完成。
- 直接持有上游模型密钥。
- 绕过 Runtime 直接调用模型网关。

浏览器里的消息只是用户体验状态。刷新页面后，页面必须重新从服务端事实恢复，而不是把浏览器缓存当作最终真相。

### Agent Runtime

Agent Runtime 是 C1 的业务执行核心。它像一位负责全程协调的事务负责人：先确认请求是谁的、是否重复、当前会话处于什么状态，再保存输入、准备上下文、调用下游、收口结果并记录证据。

Runtime 拥有：

- Conversation、Message 和 Run 的生命周期。
- 输入校验和引用校验。
- 幂等、并发和取消语义。
- Context Planner 和 Memory Manager。
- 模型调用的业务边界。
- 最终回答、usage、Context Manifest 和错误状态。

Runtime 不应该把上述职责交给浏览器或模型网关，否则多个渠道会形成不同的会话真相，模型网关也会逐渐承载它不应理解的业务状态。

### GatewayClient、AI SDK 和 LiteLLM

这三者属于 Runtime 下游的模型调用段，可以把它们理解为三层适配：

- GatewayClient 是 Runtime 依赖的统一模型客户端，屏蔽具体调用方式。
- AI SDK 把平台消息转换为模型 SDK 能理解的输入，并处理生成或流式生成。
- LiteLLM 收口模型别名、上游地址、密钥和兼容协议，再把请求转发给真实模型。

它们解决的是“怎样调用模型”，不是“怎样管理业务会话”。LiteLLM 不应该保存 Conversation、Message、Run 或长期记忆。

### SQLite 会话事实源

SQLite 保存当前版本中最重要的业务事实：会话、原始消息、Run、结构化记忆、Episode、Context Manifest 和会话事件。

“事实源”意味着发生争议时以这里保存的状态为准。例如：

- 页面显示回答完成，但 Run 仍是 `running`，服务端事实说明它还没有完成。
- 页面因刷新丢失了生成状态，但 Run 已经是 `completed`，重新加载后应恢复完成结果。
- 用户重复提交同一个请求，数据库中已有相同 `requestId` 的 Run，系统应该重放既有结果，而不是重新调用模型。

## 六类身份分别解决什么问题

C1 中存在多个 ID，不是因为设计者喜欢增加字段，而是因为它们标识的对象不同。

| 标识 | 标识的对象 | 它回答的问题 |
| --- | --- | --- |
| `conversationId` | 一段持续会话 | 这些消息和 Run 属于哪一段对话？ |
| `messageId` | 一条已持久化消息 | 被引用、纠正或展示的是哪条事实？ |
| `clientMessageId` | 渠道准备提交的用户消息 | 网络重发时是不是同一条用户消息？ |
| `requestId` | 一次有幂等语义的 Run 请求 | 这个业务请求是不是已经执行过？ |
| `runId` | 服务端创建的执行实例 | 当前执行、取消和最终状态是哪一个？ |
| `chainTraceId` | 一条业务执行链的观测身份 | 这一轮经历了哪些阶段、尝试和错误？ |

可以这样区分它们：

- `clientMessageId` 防止同一句用户消息重复入库。
- `requestId` 防止同一个业务请求重复调用模型。
- `runId` 让服务端状态可以被查询和取消。
- `chainTraceId` 让观测系统可以关联整条执行链。

如果只保留一个“万能 ID”，消息去重、业务幂等、运行状态和观测重放就会被混为一件事，很多边界将无法说清。

## 一次正常 Run 究竟发生了什么

下面继续使用第三轮问题：“我们为什么选择当前的消息队列？”

### 第一步：渠道提交当前输入

浏览器提交当前输入、`conversationId`、`requestId` 和 `clientMessageId`。它不会把整个本地聊天记录重新发送给 Runtime，因为浏览器不是会话事实源。

这样设计有三个直接收益：

- 防止旧页面把过期历史覆盖服务端最新事实。
- 防止不同标签页各自维护一套不一致的上下文。
- 避免用户篡改浏览器请求，把并不属于当前会话的内容伪装成历史消息。

### 第二步：Runtime 校验输入和会话

Runtime 先判断：

- 会话是否存在并且仍为 `active`。
- 当前输入是否至少包含文本、图片、文档链接或受支持引用中的一种。
- 标识是否完整。
- 引用的消息是否属于当前会话。
- 当前引用类型是否属于稳定契约。

输入无效时应尽早返回明确错误，不能先调用模型再尝试补救。

### 第三步：同一会话进入串行队列

如果两个标签页同时向同一个会话提交问题，Runtime 当前会按 `conversationId` 串行执行。

原因不是模型不能并行，而是第二个问题的上下文可能依赖第一个问题的最终回答。如果两个 Run 并发读取相同快照，可能形成下面的错误顺序：

```text
用户问题 A
用户问题 B
助手回答 B
助手回答 A
```

串行执行保证一个会话内保持完整的 `user -> assistant` 轮次。不同会话之间仍然可以并行，因此不会因为某个长回答阻塞所有用户。

当前边界只覆盖同一个 Runtime 进程。未来横向部署多个 Runtime 实例时，还需要分布式 lease 或按会话分区的消息队列，不能误以为进程内锁已经解决了所有并发问题。

### 第四步：先保存用户消息和 Run

Runtime 会在调用模型之前先保存用户消息并创建 Run。

这是 C1 最关键的顺序之一。它意味着即使模型随后超时，系统仍然知道：

- 用户确实提交过什么。
- 哪个 Run 没有完成。
- 下一次重发是否命中同一个请求。
- 错误属于输入阶段、模型阶段还是交付阶段。

如果先调用模型、成功后才保存用户消息，那么进程在模型调用后崩溃时，用户输入和模型消耗都可能没有可靠记录，重发还可能再次产生费用。

### 第五步：Context Planner 选择本轮上下文

模型本身并不知道“当前会话”。它每次只能看到 Runtime 为这一轮准备的消息集合。

Planner 会把候选内容按优先级装入有限预算：

1. 系统、安全和权限规则。
2. 当前用户输入。
3. 用户显式引用的会话消息。
4. active 的关键目标、约束、最新事实、决策和未完成任务。
5. 与当前问题相关的旧 Episode。
6. 最近尚未压缩的完整对话消息。

第三轮问题中，第二轮形成的 active 事实“当前项目使用 Kafka”和原因“需要事件回放”应该优先进入上下文；第一轮的 RabbitMQ 已被标记为旧事实，不应继续作为当前结论影响回答。

Planner 的价值不是“把信息拼起来”，而是在预算不足时做可解释取舍。每个候选要么完整入选，要么带原因排除，不能从字符串中间随意截断后交给模型猜测。

### 第六步：必要时先压缩，再重新规划

随着对话增长，最近原始消息窗口会逐渐接近 Token 上限。系统使用高低水位管理压缩时机：

- 达到高水位：后台从最老的完整轮次开始提取结构化记忆和 Episode，逐步把动态窗口降到低水位。
- 接近硬水位：当前回答前必须同步完成必要压缩，然后重新规划上下文。
- 低于高水位：不为了“看起来整洁”频繁摘要，避免无意义的模型调用和记忆漂移。

高低水位的目的不是删除历史。原始消息仍然保留，压缩只是产生更适合后续装箱的结构化视图。

### 第七步：调用模型

Runtime 把 Planner 选择出的上下文交给 GatewayClient，再经过 AI SDK 和 LiteLLM 到达上游模型。

这一段需要保留的核心语义包括：

- 消息角色和内容不能失真。
- 模型别名要能解析到实际模型。
- 输出 Token 上限和结构化输出约束不能丢失。
- 最终要返回实际模型、usage 和 finish reason。
- 模型错误要转换成平台能够理解的稳定分类。

模型返回的内容在这一刻仍然只是生成结果，还没有自动成为会话最终事实。

### 第八步：通过 POST SSE 增量交付文本

流式回答通常经历以下事件：

```text
run-started
  -> text-delta
  -> text-delta
  -> ...
  -> completed / cancelled / error
```

`text-delta` 只在内存和网络层流动，系统不会每收到一个 Token 就写一次 SQLite。原因是逐 Token 落库会造成大量小事务，也会制造难以处理的半成品消息。

正常完成时，Runtime 把完整助手回答、Run 最终状态、usage 和 Context Manifest 在收口阶段持久化。最终只有一条完整助手消息，而不是几十或几百条 Token 片段。

### 第九步：最终事实收口

只有当模型生成、结果整理和存储提交都完成后，Run 才进入 `completed`。

这里必须区分两个概念：

- 用户已经看见部分文字，表示“输出已经开始”。
- 服务端完成事务提交，表示“最终事实已经形成”。

页面可以为了体验即时展示增量，但最终仍要以服务端 Conversation、Message 和 Run 为准。

### 第十步：异步更新结构化记忆

回答完成后，Memory Manager 可以根据水位异步处理已经提交的完整消息，提取 MemoryDelta 和 Episode。

它不会在长时间模型调用期间持有数据库事务。提取结果提交时使用 `memoryVersion` 和消息水位进行乐观锁校验：如果另一个任务已经更新过记忆，旧任务不能覆盖新结果，而是重新读取后只处理尚未压缩的区间。

这说明记忆更新是最终一致的：主回答可以先完成，结构化记忆稍后更新；但任何记忆都必须能够追溯到原始消息。

## 原始消息、结构化记忆、Episode 和上下文

这四个概念很容易被混淆。

### 原始消息是不可替代的事实

原始消息记录用户和助手实际说过什么。它们只追加，不因摘要或纠正而删除。

在贯穿案例中，下面两句话都会保留：

```text
当前项目使用 RabbitMQ。
更正一下，当前项目使用 Kafka，因为需要事件回放。
```

保留旧消息并不意味着旧结论仍然有效，而是为了审计、来源追溯和必要时重建记忆。

### 结构化记忆是从事实中提取的当前视图

结构化记忆把长期有价值的信息组织为目标、约束、偏好、事实、决策和任务。

纠正发生后，可以形成这样的逻辑状态：

```text
事实 A：当前项目 / 消息队列 / RabbitMQ / superseded
事实 B：当前项目 / 消息队列 / Kafka / active
原因：需要事件回放
来源：第 2 轮用户消息
```

旧事实没有消失，只是不再作为当前有效事实使用。这样既保留审计能力，也避免模型继续把旧值当作最新结论。

### Episode 是一段经历的主题摘要

Episode 适合表达“某一段时间讨论过什么以及得出了什么结果”，例如：

```text
主题：消息队列决策
摘要：用户将当前项目的消息队列从 RabbitMQ 更正为 Kafka，原因是需要事件回放。
来源区间：第 1 至第 2 轮
```

它与结构化事实的区别是：事实适合精确读取当前值，Episode 适合召回较早发生的一段讨论。

### 本轮上下文只是一次临时装箱结果

上下文不是数据库中的全部历史，也不是永久记忆。它只是针对当前问题，从系统规则、引用、记忆、Episode 和最近消息中选择出的临时输入集合。

同一会话中的不同问题可能得到不同上下文：

- 问“为什么选择 Kafka”时，应选中消息队列决策和原因。
- 问“当前还有哪些待办”时，应优先选择 active task。
- 问完全无关的问题时，不应因为记忆中存在 Kafka 就强行注入。

Context Manifest 则是本轮装箱的说明书，记录预算、实际计数方式、入选内容和排除原因。它不是 Prompt 正文的副本，也不应该复制敏感内容。

## Token 预算真正控制的是什么

模型上下文窗口不是可以随意塞满的无限空间。当前默认策略可简化理解为：

```text
最大上下文                 12000
预留模型输出                2000
安全余量                     500
其余空间才用于输入装箱
```

输入预算内部还要分给系统规则、当前输入、引用、结构化记忆、Episode 和最近历史。Token 控制要回答的不是“这次一共用了多少”，而是：

- 哪类信息占用了多少？
- 为什么关键事实被保留？
- 为什么低优先级历史被排除？
- 是否为了无关历史浪费了成本和延迟？
- 输出预算是否足够让模型完成回答？

Token 越少不一定越好。删掉关键纠正会损害准确度；Token 越多也不一定越好，无关信息会增加费用、延迟和模型注意力干扰。所谓 Token 合理性，是用刚好足够的高价值上下文完成任务，并且能够解释取舍。

## 幂等不是“简单去重”

幂等的含义是：同一个业务请求无论提交一次还是重复提交，最终业务效果应该一致。

### 为什么请求会重复

重复通常不是用户故意点击两次，而是调用方无法确认第一次是否成功：

- 请求已经到达服务端，但响应在网络中丢失。
- 页面超时后自动重发。
- 用户刷新页面后恢复操作。
- 网关或代理重复投递。

此时系统不能仅凭“客户端没有收到响应”就认定第一次没有执行。

### C1 的幂等结果

相同 `requestId` 已经对应一个 Run 时，再次提交应该返回既有 Run 结果，而不是创建第二个模型调用。相同 `clientMessageId` 也不能再次写入一条相同用户消息。

这同时保护三件事：

- 用户不会看到重复消息。
- 会话轮次不会被污染。
- 模型调用不会重复计费。

幂等必须依赖服务端持久化事实和唯一约束，不能只依赖浏览器把按钮临时禁用。

## 重试为什么必须有边界

“失败就重试”是危险的。C1 只对明确的瞬时错误，在总截止时间内，并且尚未产生有效输出时进行模型重试。

当前模型调用的基本策略是：

```text
总尝试次数：最多 3 次
总截止时间：120 秒
退避方式：指数退避加随机抖动
可重试错误：瞬时网络错误、408、429、500、502、503、504
关键边界：只允许在首个有效输出之前重试
```

### 为什么需要共享总截止时间

120 秒属于整个 Run，不是每次模型尝试都重新获得 120 秒。这个预算还要覆盖接入、排队、上下文规划、模型尝试、持久化和交付。

如果三次尝试各自拥有完整 120 秒，用户最坏可能等待六分钟以上，而且上层、AI SDK 和 LiteLLM 的重试还可能继续相乘。

因此只能有一层拥有主要重试预算。当前由平台统一重试执行器控制，AI SDK 自带自动重试保持关闭。

### 为什么首个有效输出后停止自动重试

假设用户已经看到：

```text
我们选择 Kafka 的主要原因是……
```

此时模型连接失败。如果系统静默重新调用模型，新模型回答可能从另一种措辞和论证结构开始。把两次生成拼接起来，会形成内容重复、前后矛盾甚至语义断裂。

所以 `outputStarted` 是不可逆边界：输出开始前，可以把失败的一次尝试替换为新尝试；输出开始后，只能明确终止或失败，不能假装仍是同一次连续生成。

## 流式交付、事实同步和 JSON Run 是三件事

### POST SSE 模型文本流

它服务于当前这一次回答，让用户尽快看到文本增量。它是低延迟交付通道，不是长期事实源。

### 会话事实事件流

它基于服务端已持久化事件和游标，同步 Conversation、Message 和 Run 的事实变化，适合多个标签页恢复一致状态。

### JSON Run

它适合服务端调用、自动化测试、批处理式等待和幂等结果查询。JSON 与 POST SSE 不是两条不同业务链，它们共用同一个 Runtime、Run 和 Store，只是交付方式不同。

这三者不能混为一体。文本增量不等于已持久化事实，事实事件也不等于外部实时事件处理场景。

## 取消、断连和失败的区别

### 用户显式取消

用户点击停止后，渠道调用取消端点，Runtime 中止当前模型调用、退避等待和尚未开始的重试。

- 尚未产生非空文本：Run 进入 `cancelled`，不创建空助手消息。
- 已经产生部分文本：Run 进入 `cancelled`，最多保存一条 `interrupted` 助手消息。
- 重复取消：返回当前终止状态，不重复改写数据。

中断消息默认不作为后续普通 Run 的可信历史，因为它可能是不完整结论。用户显式引用它时，系统才可以带着“这是中断内容”的状态装入上下文。

### 浏览器断连

刷新页面、网络中断或关闭 SSE 连接，只能说明用户暂时收不到当前流，不能证明用户希望停止生成。

Runtime 应继续完成或失败，浏览器恢复后通过 `latestRun` 查询最终状态。把断连等同取消，会导致移动网络抖动时大量任务被意外终止。

### 普通失败

输入错误、权限错误、模型超时、限流、网关不可用、空响应和存储失败应具有不同分类。只有分类明确，系统才能决定：

- 是否应该重试。
- 应该向用户显示什么安全文案。
- Run 最终进入什么状态。
- 告警和统计应该归入哪类问题。

## 引用为什么不能只传一段正文

当前 C1 支持引用当前会话中已经持久化的消息。渠道提交的是带类型的引用对象和 `messageId`，Runtime 再从事实源读取真实内容。

不能信任浏览器重复提交的引用正文，因为正文可能：

- 被用户篡改。
- 来自另一个会话。
- 已经不是服务端保存的版本。
- 隐含当前用户无权访问的信息。

Runtime 还必须拒绝未知引用类型。文档片段、网页快照、业务记录和工具结果具有不同的所有者、版本、时效和权限语义，不能全部降级成一个通用 `sourceId` 或直接拼入 Prompt。

## ChainTrace 怎样解释一次请求

日志经常只能看到分散的几句话，ChainTrace 则把一次 Run 的阶段和因果关系连接起来。

一条 C1 Trace 应能够覆盖：

```text
C1 根执行
  -> 队列等待
  -> 创建或命中 Run
  -> Context Planner
  -> 可选记忆压缩与重新规划
  -> 模型尝试 1
  -> 可选模型尝试 2、3
  -> 最终结果持久化或失败收口
  -> JSON / SSE 交付
```

通过 `requestId + conversationId + runId`，维护者应该能够回答：

- 请求有没有排队？
- Planner 花了多久？
- 本轮选择了多少 Token？
- 模型实际尝试了几次？
- 首个文本增量何时出现？
- 最终是模型失败、存储失败还是交付失败？

Trace 是观测旁路，不是业务事实源。观测后端宕机不应改变 Run 行为，也不能反过来修改 Conversation、Message 或 Memory。

Trace 默认不记录 Prompt、回答、图片地址、文档地址、原始错误正文或调用栈，只记录稳定身份、阶段、时长、计数和脱敏错误分类。可观测不等于无限采集，尤其不能以排障为由复制敏感会话正文。

## 怎样判断 C1 是否真的可用

“模型返回了内容”最多证明网络和协议基本连通，不能证明 C1 已经完成。

### 准确度

需要验证：

- 最新纠正是否覆盖旧事实。
- 相似实体之间是否隔离。
- 未完成任务的状态是否正确。
- 回答使用的来源是否仍然有效。
- 失败案例是否能够稳定复现。

贯穿案例中，第三轮回答应该指出 Kafka 和事件回放，不能继续回答 RabbitMQ，也不能把另一个项目的 RabbitMQ 混入当前项目。

### 实时性

不能只记录总耗时，需要区分：

- 接入和校验耗时。
- 同会话排队耗时。
- Context Planner 耗时。
- 模型首个有效输出时间。
- 模型完成时间。
- 持久化和最终交付时间。

只有阶段拆开，才能判断优化目标究竟是数据库、上下文规划、模型还是网络交付。报告时至少关注 P50 和 P95，而不是只看一次最快结果。

### 稳定性

至少要覆盖：

- 空输入和非法引用。
- 重复请求和重复取消。
- 同会话并发。
- 模型超时和网关错误。
- 限流与 `Retry-After`。
- 首增量前失败和首增量后失败。
- 用户取消和浏览器断连。
- 空模型响应。
- 记忆版本冲突。

稳定性的目标不是“永远不失败”，而是每类失败都有确定、可解释、可恢复且不产生重复副作用的状态。

### Token 合理性

需要同时查看：

- 系统规则 Token。
- 当前输入 Token。
- 显式引用 Token。
- 结构化记忆 Token。
- Episode Token。
- 最近历史 Token。
- 模型输出 Token。
- 被排除候选及原因。

如果回答准确但每次都装入全部历史，成本和延迟会不断上升；如果 Token 很少但漏掉最新纠正，也不能算合理。

## 两类评测不能互相替代

### 确定性 Runtime 回归

确定性评测使用脚本模型或固定返回，重点验证：

- 消息和 Run 状态是否正确。
- Reducer 是否正确维护 `active/superseded`。
- Planner 是否选择了预期候选。
- checkpoint 和水位是否正确推进。
- 幂等、并发和错误分支是否符合契约。

它的优势是稳定、快速、便宜，失败时容易定位。但是它不能证明真实模型理解了问题。

### 真实模型评测

真实模型评测需要固定：

- fixture 版本。
- 模型别名和实际模型。
- Prompt 版本。
- 采样参数和输出上限。
- 上下文与记忆策略。
- 评测时间和运行环境。

结果至少报告通过数/总数、准确率、旧事实泄漏率、实体隔离准确率、任务状态准确率、来源有效率、Token、费用、平均延迟和 P95 延迟。样本不足 30 时，只能报告观察结果，不能把偶然结果宣布为稳定准确率。

确定性回归回答“平台逻辑是否按设计运行”，真实模型评测回答“在这个固定模型和策略下，实际效果是否达到要求”。两者缺一不可。

## C1 当前不包括什么

理解边界和理解主链同样重要。当前 C1 不代表项目已经具备：

- 文档解析、向量检索或 RAG。文档 URL 当前只是文本链接。
- 真实业务 API 或 MCP 工具循环。
- 外部实时事件消费。当前 SSE 是回答交付和会话事实同步。
- 有副作用的业务操作和人工确认。
- 图片资产治理和完整视觉评测。
- 批量分片、断点恢复和异步产物管理。
- 多 Runtime 实例下的分布式会话串行。

这些分别属于后续场景或下一阶段底座能力。不要因为共同底座已经存在，就把其他场景误认为已经完成。

## 建议的文本学习顺序

### 第一阶段：建立链路全貌

重点理解参与者、数据所有权和完整执行顺序。不要急着记住技术名词，先能复述：

```text
渠道只提交当前输入
Runtime 保存事实并组织执行
Planner 选择本轮上下文
Gateway 段负责调用模型
Store 保存最终状态
Trace 和评测提供证据
```

掌握标志：能够解释为什么浏览器和模型网关都不能成为会话事实源。

### 第二阶段：理解状态和恢复

重点理解 Conversation、Message、Run、六类 ID、幂等、同会话串行、取消、断连和重试边界。

掌握标志：给出“重复提交、429、首增量后断开、用户取消”四个案例时，能够分别说明最终状态和是否允许重试。

### 第三阶段：理解上下文和记忆

重点理解原始消息、结构化记忆、Episode、本轮上下文、Context Manifest 和高低水位。

掌握标志：能够解释 RabbitMQ 被纠正为 Kafka 后，旧消息为何保留、旧事实为何不再生效、第三轮上下文应该选择什么。

### 第四阶段：理解质量证据

重点理解 ChainTrace、四维指标、确定性回归与真实模型评测。

掌握标志：面对“模型返回了正确答案”这一结论时，能够继续追问模型版本、fixture、通过数、Token、P95、失败案例和链路阶段证据。

## 用场景题检验是否真正理解

### 场景一：页面超时后重发

服务端已经完成模型调用，但响应没有到达浏览器。浏览器使用相同 `requestId` 和 `clientMessageId` 重发。

正确判断：返回既有 Run 和消息，不新增用户消息，不再次调用模型。因为网络结果不确定不代表服务端没有执行。

### 场景二：模型在首个文字前返回 429

正确判断：如果仍在 Run 的总截止时间内，可以根据 `Retry-After` 和统一退避策略重试，最多不超过总尝试预算。

### 场景三：模型已经输出一段文字后连接失败

正确判断：不能静默重新生成并拼接。输出已经跨过不可重放边界，应明确失败或中断并保留确定状态。

### 场景四：用户关闭浏览器标签页

正确判断：这只是连接断开，不是显式取消。Runtime 继续执行，用户回来后查询 `latestRun` 恢复最终状态。

### 场景五：用户点击停止

正确判断：取消当前模型调用、退避和后续重试。没有文本时不创建空助手消息；有部分文本时最多保存一条 `interrupted` 消息。

### 场景六：用户引用另一会话的一条消息

正确判断：Runtime 拒绝引用。渠道提交的 `messageId` 必须由服务端验证归属和权限，不能相信浏览器提供的正文。

### 场景七：确定性 100 轮评测全部通过

正确判断：可以说明 Runtime、记忆 Reducer、Planner 和判分逻辑通过回归，不能据此宣布真实模型准确率已经达标。

### 场景八：回答正确，但上下文装入了全部历史

正确判断：准确度可能暂时通过，但 Token 合理性、延迟和长期可扩展性不合格，仍不能认为 C1 已完成。

## 最终应该形成的系统认识

理解 C1 之后，不应把它描述成：

> 浏览器把聊天记录发送给大模型，大模型流式返回回答。

更准确的描述是：

> 渠道把带稳定身份的当前输入提交给 Agent Runtime。Runtime 以持久化消息为事实源，在同一会话内串行创建幂等 Run，通过 Context Planner 从显式引用、active 结构化记忆、相关 Episode 和最近消息中构造预算内上下文，再经 GatewayClient、AI SDK 和 LiteLLM 调用上游模型。模型文本通过 POST SSE 增量交付，但最终只持久化一条完整或明确中断的助手消息。整个过程受共享截止时间、首输出前重试、显式取消、错误分类和数据一致性规则约束，并通过 ChainTrace、Context Manifest、确定性回归和真实模型四维基线提供可验证证据。

当这段描述不再只是需要背诵的文字，而是每个设计选择都能回答“为什么”，就真正理解了 C1 链路。
