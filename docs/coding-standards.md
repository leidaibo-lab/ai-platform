# 编码规范

本规范约束项目中的新增代码和存量代码修改。目标是让代码的职责、数据边界和设计依据可以直接从代码与变更说明中读出，而不是依赖实现者口头补充。

## 函数注释

所有函数都必须有紧邻的注释，包括：

- 命名函数和导出函数。
- 类的构造函数、实例方法和静态方法。
- 赋值给变量或对象属性的箭头函数。
- 作为参数传入的回调函数。

导出函数、公共方法和复杂函数使用 JSDoc，至少写清职责，并根据实际情况补充参数、返回值、副作用和异常：

```js
/**
 * 根据上下文预算构造发送给模型的消息列表。
 *
 * @param {BuildMessagesInput} input - 摘要、历史消息、当前消息和预算配置。
 * @returns {BuildMessagesResult} 消息列表及预算使用情况。
 */
export function buildMessagesWithBudget(input) {
  // ...
}
```

简单内部函数和回调函数可以使用单行职责注释，但不能省略：

```js
// 只保留具有合法角色和非空正文的历史消息。
const validMessages = messages.filter((message) => isValidMessage(message));
```

注释必须解释函数为什么存在、负责什么或受什么边界约束。禁止只把函数名或代码逐句翻译成自然语言；行为变化后必须同步更新注释。

## 数据结构

- 跨模块传递的配置、请求、响应和领域对象，使用 JSDoc `@typedef` 或同等结构化方式明确字段、类型、可空性和嵌套关系。
- 定义数据结构时说明不变量，例如允许的角色集合、必填字段、长度或数值范围、去重和顺序要求。
- 明确数据所有权和可变性。默认返回新对象或新数组；确需原地修改时，在函数注释中说明副作用。
- 根据访问方式选择结构：键查找使用 `Map`，唯一集合使用 `Set`，有序序列使用数组；不要用含义不明的松散对象或相互依赖的平行数组代替明确模型。
- 外部输入先归一化和校验，再进入核心逻辑；核心逻辑不反复猜测同一字段的类型和默认值。

## 设计模式

设计模式用于解决明确的变化点、依赖边界或复用问题，不是每个模块都必须附加的形式要求。

- 引入模式前先写清要解决的问题；简单纯函数能够表达的逻辑保持简单。
- 使用工厂、适配器、策略、注册表或依赖注入等模式时，在模块注释或架构文档中说明模式名称、参与角色和扩展点。
- 模式边界与目录和模块职责保持一致，不为单一实现预留未经验证的抽象层。
- 评审时检查模式是否降低了分支复杂度、耦合或测试成本；没有实际收益的抽象应删除。

## 设计原则

- 单一职责：函数和模块只承担一个可描述的主要职责。
- 高内聚、低耦合：相关逻辑集中，跨层依赖通过清晰接口传递。
- 依赖倒置：运行时逻辑依赖 gateway client 等抽象能力，不直接散落外部请求细节。
- KISS：优先选择能够直接读懂和验证的实现。
- DRY：消除会导致行为不一致的重复规则，不为表面相似代码过早抽象。
- YAGNI：不实现当前需求和稳定契约未要求的扩展能力。
- 边界分离：外部 I/O、输入校验、数据转换和核心业务逻辑分层处理。

## 变更检查

交付前检查本次变更涉及的全部文件：

- 每个函数都有与当前行为一致的职责注释。
- 公共或跨模块数据结构有明确的结构定义和字段约束。
- 变更说明指出使用或未使用设计模式的理由，不能只写“符合设计模式”。
- 变更说明列出实际采用的设计原则及对应代码依据，不能只罗列原则名称。
- 输入校验、外部 I/O 和核心逻辑边界清晰，必要的测试或 smoke test 已更新并通过。

本规范属于工程协作约束，不改变 AI Gateway 的接口、配置和安全边界，因此无需单独修改稳定 OpenSpec；当具体代码变更影响稳定能力契约时，仍按 `AGENTS.md` 的 OpenSpec 规则同步更新。
