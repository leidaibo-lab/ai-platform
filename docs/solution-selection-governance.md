# 方案选型与复用治理

## 目的

AI 应用基础平台的价值不是重新实现一套通用 AI 基础设施，而是为真实业务选择成熟能力，完成必要的组合、边界适配、治理和统一出口，并把经过验证的决策沉淀成可复用的组织资产。

本项目使用“先发现、再决策、后实现”的顺序，避免把“能够实现”直接等同于“应该自研”，也避免能力交付只停留在代码完成。每次重要选择都必须能回答：业内还有哪些方案，哪些方案可能更完整或更内聚，最终为什么采用当前方案，为什么没有采用其他方案。

## 核心原则

1. **先研究后实现**：没有完成问题定义、方案发现和关键假设验证，不进入正式实现。
2. **采用优先于适配，适配优先于自研**：优先复用成熟产品、框架、协议和基础设施；差异通过 Adapter、Port 或插件边界解决。
3. **平台负责组合，不默认拥有所有实现**：平台应拥有内部稳定契约、企业边界、治理规则和替换能力，不默认拥有每个底层算法或执行引擎。
4. **比较真实闭环，不比较宣传功能**：使用当前场景的主路径、异常路径、数据边界和运维要求验证候选，不以功能列表或最小 Hello World 作为结论。
5. **记录未采用原因**：方案决策不仅说明“用了什么”，还要说明“为什么没有用其他方案”，避免后续反复讨论或在缺少上下文时重做选择。
6. **保留退出路径**：引入成熟方案时也要识别数据所有权、供应商锁定、迁移成本和替换边界，不以增加依赖数量代替架构判断。
7. **决策可以演进但不能失忆**：方案过时或约束变化时新增记录并标记替代关系，不覆盖或删除原决策。

## 适用范围

以下变更必须执行本治理流程：

- 新增一个平台级或跨模块公共能力。
- 引入、替换或升级会影响架构边界的重要框架、服务或基础设施。
- 自研会话、任务编排、记忆、检索、工具执行、重试恢复、可观测、评测、鉴权、网关等通用机制。
- 把当前模块拆成服务，或者改变数据所有权、运行时主链和长期维护责任。
- 已有实现出现重复建设、维护成本、能力缺口或更成熟替代方案，需要决定保留、封装、迁移或替换。

局部缺陷修复、文案和样式调整、已有稳定方案内的等价实现细节不强制新建记录；一旦影响稳定契约、外部依赖、数据边界或公共行为，仍应进入本流程。

## 决策流程

### 1. 定义问题

先写清楚业务目标、目标用户、当前损耗、成功证据、硬约束和非目标。能力名称或待写代码不能代替问题定义。

### 2. 建立候选池

默认至少检索三类路线：

| 路线 | 需要回答的问题 |
| --- | --- |
| 成熟一体化方案 | 是否已经内聚覆盖相邻能力、状态生命周期、异常恢复和观测，能否整体采用 |
| 轻量可组合方案 | 是否可以复用核心引擎或协议，由平台保留自己的稳定契约和数据所有权 |
| 最小自研方案 | 真正必须自研的差异是什么，长期维护和演进成本由谁承担 |

候选证据优先使用官方文档、源代码仓库、许可证、安全与部署说明、版本发布记录和真实生产案例。二手文章可以帮助发现方案，不能单独支撑最终决策。

### 3. 识别淘汰条件

先检查不可妥协的约束，再做综合比较。常见淘汰条件包括：

- 无法满足私有部署、数据驻留、鉴权或审计要求。
- 破坏项目单向依赖、稳定契约或事实数据唯一所有者。
- 不支持关键异常路径、幂等、恢复或可观测要求。
- 许可证、社区维护状态或版本兼容风险不可接受。
- 必须侵入业务主链，且没有稳定 Adapter 或退出路径。

### 4. 验证关键假设

PoC 只验证会改变决策的关键问题，不追求功能齐全。至少覆盖一条真实主路径和一个最高风险边界，例如中断恢复、并发、权限隔离、数据迁移或供应商替换。记录版本、配置、输入、结果和失败证据，不能只写“可以运行”。

### 5. 做出选择

使用 `docs/decisions/TEMPLATE.md` 建立方案决策记录，明确：

- 采用、适配或自研的结论。
- 平台拥有的契约、数据和治理边界。
- 交给外部方案负责的能力。
- 未采用候选及具体原因。
- 已知风险、退出路径和重评条件。

没有被接受的决策记录，只能继续调研或 PoC，不能进入正式实现。

### 6. 实现与验收

实现范围不得默默超出已接受决策。新事实推翻原判断时，先更新或新增决策记录，再调整实现。验收同时检查功能结果、方案假设和集成边界，不能只检查代码是否通过测试。

## 评估维度

候选比较至少覆盖以下维度；具体权重由场景决定，不使用统一总分掩盖淘汰条件：

| 维度 | 关键问题 |
| --- | --- |
| 场景适配 | 是否解决当前真实问题，而不是泛化能力看起来更多 |
| 能力内聚 | 是否完整拥有相关状态和生命周期，能否减少多个局部实现之间的拼接成本 |
| 架构边界 | 是否符合 Runtime、连接器、模型网关和治理区域的依赖与数据所有权 |
| 成熟度 | 发布节奏、兼容承诺、社区和生产案例是否足以承担关键链路 |
| 安全与部署 | 私有部署、密钥、权限、审计和数据驻留是否可控 |
| 可靠性 | 超时、重试、幂等、恢复、并发和降级是否有明确语义 |
| 可观测与评测 | 是否能关联输入、状态、成本、错误和质量证据 |
| 扩展与锁定 | 扩展点是否稳定，核心数据能否导出，替换成本是否可接受 |
| 总拥有成本 | 采购、集成、运行、升级、排障和长期维护成本是否优于替代路线 |

## 自研准入条件

自研通用能力必须至少满足以下一项，并在决策记录中提供证据：

- 该能力承载项目的核心差异化，成熟方案无法表达关键业务语义。
- 数据所有权、安全、部署或合规边界排除了成熟方案。
- 成熟方案无法通过稳定适配层满足现有契约，且迁移或集成总成本明显高于自研。
- 能力足够小、边界稳定、测试明确，自研不会演变为另一个需要长期追赶生态的框架。

自研记录还必须明确维护责任、明确不实现的范围、测试与观测证据，以及未来迁移到成熟方案的触发条件。

## 能力完成定义

能力只有同时满足以下条件才能报告“完成”：

1. 问题、约束和非目标已经明确。
2. 候选方案、检索依据和关键差异已经记录。
3. 关键假设已经通过 PoC、测试或生产证据验证。
4. 最终选择和未采用原因已经形成接受状态的方案决策记录。
5. 实现没有超出决策边界，相关 OpenSpec、文档和测试已经同步。
6. 交付说明包含验证结果、剩余边界、维护责任和重评条件。

交付通知使用以下结构，不能只写“已完成对应能力”：

```text
能力目标：
调研候选：
最终选择：采用 / 适配 / 自研
选择依据：
未采用方案及原因：
平台自研范围：
验证证据：
剩余边界：
维护责任：
重评条件：
```

## 存量能力审计

既有实现不因已经运行而自动获得合理性，也不因缺少历史记录而立即替换。缺少决策证据的能力先标记为“待补选型证据”，通过审计后分别处理：

| 处理结论 | 含义 |
| --- | --- |
| 保留 | 当前方案仍适配，补齐采用依据、边界和重评条件 |
| 封装 | 保留现有实现，但通过稳定 Port 或 Adapter 降低耦合并准备替换 |
| 迁移 | 成熟方案在关键维度明显更优，制定兼容、数据迁移和回退计划 |
| 停止 | 能力没有真实需求或维护价值，停止继续扩展并说明影响范围 |

当前优先审计 Agent Runtime 编排、结构化记忆与 Context Planner、重试与恢复、流式交付、可观测与评测、工具执行。LiteLLM 和 AI SDK 已体现成熟能力复用方向，但仍需在项目内补齐可追溯的采用依据，不能用此前口头讨论代替决策记录。

存量审计期间不冻结必要缺陷修复，但暂停在未完成审计的区域继续增加新的通用抽象。审计目标不是追求全面替换，而是明确哪些能力由平台拥有、哪些交给成熟生态，以及两者之间的稳定边界。

## 与其他治理文件的关系

- `docs/decisions/` 保存为什么这样选择以及为什么没有选择其他方案。
- `openspec/` 保存最终对外稳定的行为和安全契约。
- `docs/ai-structure.md` 保存能力归属、依赖和数据所有权。
- `docs/coding-standards.md` 约束选定方案进入代码后的实现质量。
- `README.md` 面向使用者说明已经可用的能力，不承载内部候选方案讨论。
