# 单场景产研闭环实施设计

交付边界已调整为向 `main` 创建 MR 并记录回执。下文测试环境发布部分保留为前期试验和后续建设参考。本阶段目标见[产研主架构](./harness-architecture.md#总体结构)。

状态为提案。以单实例、单项目、一个业务场景完成产品、研发、测试、外部测试环境发布及交付为目标。沿用工作台现有的业务确认、测试确认和发布确认。企业身份、项目权限与审批授权安排在业务闭环验收之后。见[三层 Harness 决策](../decisions/2026-11-19-three-layer-harness.md)。

## 第一批 · 让返工有明确去向

首轮验收建议选现有测试场景中的一条业务规则。先批准规则并实施，在测试审阅时发现规则本身有误。用户在工作台确认新口径，随后检查研发、回归和发布是否全部基于新版本。现有 `qa-business-gap` 和 `stable-revision` 已覆盖原生工作流的基本回流。首轮开发补齐跨团队交接证据和工作台呈现。见[主线 OpenSpec](../../openspec/specs/project-mainline/spec.md)与[全链路回归](../../tests/unified-workflow.test.ts)。

| 用户遇到的情况 | 谁判断与执行 | 工作台要展示的事实 |
| --- | --- | --- |
| 产品生成中误解了范围 | 平台持久化纠偏并停止本次尝试。产品团队决定从澄清、分析或写稿等已有节点重做 | 沿用「立即纠偏」。保存后显示待应用，真正进入重做时显示已从哪个节点应用，新稿进入审阅 |
| 测试发现实现违反了已确认规则 | 测试提交缺陷与证据，研发团队决定从哪个内部节点修复 | 显示退回研发。保留现行产品确认，新候选重新验证 |
| 测试发现已确认的规则本身有误 | 测试提交关联需求与失败证据，主 Workflow 按现有规则送入产品澄清，产品团队组织修订 | 显示退回原因、待确认的业务问题、受影响阶段。旧证据保留为历史，修订确认后显示新有效基线与重跑阶段 |
| 修订需要扩大原 Run 的写入范围，或来源 Run 已结束 | 主 Workflow 校验执行边界。符合现有来源与 Git 回执条件时，使用后继 Run 入口 | 显示当前阻塞原因与来源规格。新 Run 从明确变更和确认开始 |

先复用测试结果中的发现 ID、需求引用、候选版本与质量审阅证据，连到现有澄清问题和修订稿。明确属于业务的发现必须对应具体需求或标明现有规格缺项，无法定位时保留为待澄清。产品团队说明规则改动，研发和测试分别依据修订基线决定自己的重做范围。首轮按现有依赖重走研发和 QA，有效上游规格可以沿用，旧验收结果仅供参考。主 Workflow 以确认版本和依赖关系判定证据是否仍有效。见[测试团队](../../src/delivery/testing.ts)、[产品返工](../../src/mastra/workflows/product-rework.ts)、[阻塞澄清](../../src/intake/blocker-workflow.ts)和[后继 Run](../../src/intake/successor-run.ts)。

实施入口依次是 OpenSpec 中的业务回流契约、测试发现与阻塞的映射、`run-timeline.ts` 和工作台投影。先让原生快照提供「待确认」「修订已确认」「已进入重跑」的判断依据，再通过 SSE 刷新页面。验收时在澄清等候期间断线重连，从快照恢复同一状态。回放旧版确认和旧候选测试结论，验证它们均无法进入新版发布。

## 第一批 · 验证中断恢复及 Git 交接

平台 Harness 以原生 Run 快照与现有校验为起点。为试点记录工程提交、已确认的上下游规格、角色方法版本或摘要、当前候选散列及有效确认。恢复时在相应节点检查这些输入。兼容性以原运行版本恢复为基线，校验失败时给出具体不匹配项和恢复原配置的操作。已结束 Run 的业务演进使用现有后继 Run。见[主编排](../../src/mastra/workflows/product-development.ts)与[平台恢复](../../src/mastra/platform/workflow-recovery.ts)。

外部副作用优先验证正式规格的 Git 交接。`publishHandoff` 已有同输入复用本地提交和远端验证逻辑。用隔离仓库在「远端已接收，Workflow 尚未保存交接回执」处注入故障。在同一部署和磁盘上恢复后，核对远端分支、提交以及批准的文件散列，再落同一份回执。遇到远端分支分叉或内容漂移时停在当前阶段。若故障测试暴露本地缓存丢失后的重复提交，先在该交接点设计基于确认版本与远端已提交证据的对账。见[Git 交接](../../src/delivery/remote-handoff.ts)。

## 第一批 · 把交付证据接到测试环境

首轮用同一份通过 QA 的候选构建一次，部署到测试环境，沿用人工回填外部回执的入口。发布前核对 `产品规格版本 → 研发候选源码散列 → QA 结果 → 构建制品 digest → 发布回执 → 健康检查`。构建步骤必须能出示实际输入的 commit 或候选工作树，以及对应的制品 digest。已有回执会校验发布散列、源码散列、环境和 digest。需要补证据时先补构建输入与制品输出的关联。若实际部署必须先合并，只有合并树与 QA 候选匹配时才能沿用该结果，否则以合并后的候选重跑适用的验证。见[部署步骤](../../src/delivery/deployment.ts)与[交付生命周期决策](../decisions/2026-11-07-mastra-full-delivery-lifecycle.md)。

验收需要一份测试环境的实际构建记录、部署回执和健康记录，并做一次制品 digest 不匹配的拒绝验证。手填回执仍按当前人工报告语义展示。若试点仅拥有合成回执，则验收记录注明控制流通过，外部交付验证待执行。

## 第二批 · 用一个研发角色验证 Nacos 的共享价值

团队维护方法内容与采用版本，Nacos 分发 Prompt 和 Skill，平台保存 Run 的确切引用与内容摘要。先选研发独立代码审查的一项 Skill。新 Run 从明确配置选择版本，旧 Run 核对原命名空间、资源名、版本和内容摘要后恢复。原版不可访问或内容漂移时，给出具体资源诊断并停在可恢复节点。保护检查与验收约束继续由业务工程 Harness 的 Git 版本提供。见[Nacos 资源装配](../../src/mastra/nacos-resources.ts)与[研发方法装配](../../src/development/v2/methods.ts)。

用同一个候选验证两次。发布新版以后，新 Run 使用新版，已有暂停 Run 仍使用原版。再模拟原版不可用，验证恢复会停下且页面能定位到资源。以产品和研发两个实际使用方的共性决定提取哪些公共资源加载逻辑。

## 从第一批开始 · 用同一个场景维护评测

固定业务输入、预期需求与关键验收用例。确定性回归利用现有 `unified-workflow` 和 `harness-boundaries` 用例验证返工路由、失效判定、版本匹配与中断恢复。真实模型走一次工作台，记录能否及时纠偏、是否正确保留用户决定、哪些阶段发生重复劳动，以及模型调用量和耗时。对于方法版本升级，用相同输入与旧版对照，检查需求遗漏、严重误判、未授权写入和保护检查。通过单次真实走查先记录基线，再依据积累的结果设版本发布门槛。见[评测目录](../../evaluations/README.md)。

## 落地顺序

1. 用现有测试期业务回流跑一遍控制流，确定试点的真实业务规则、期望修订与发布证据。以同一场景覆盖产品早期纠偏和测试期发现。
2. 先提交范围最小的 OpenSpec 变更，然后补回流交接引用、工作台状态与回归。并行准备 Git 交接故障验证及测试环境构建证据。
3. 从工作台完整走到测试环境交付，核对纠偏生效时间、修订版本、Git 交接与部署结果。
4. 以同一流程验证 Nacos 第二个角色，并将方法版本对照纳入评测。公共接口的提取以实际重复为依据。
