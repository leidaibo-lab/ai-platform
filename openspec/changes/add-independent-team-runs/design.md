# 设计草案

本设计包含已接入的独立团队入口和待决扩展；实际实施、验证范围及剩余事项见 `tasks.md`。

## 输入与来源

独立团队 Run 使用 `team-run-input.v1`，以团队、项目、迭代、来源引用、预算和团队专属载荷表达请求。服务端解析权威来源并在 Mastra Store 冻结输入、项目身份和版本；客户端不能提交审批结论、候选路径、任意 Git ref 或执行命令。

产品消费原始需求或经确认的材料；研发消费已批准的产品产物或经确认的输入包；测试消费研发交付和固定候选；交付消费同版本 QA 放行及正式规格。输入包的登记、验证与人工确认需要在实现前进一步细化，不能把文件或登记表当作审批事实源。

### 外部候选材料：待决接入设计

当前输入包只登记原始产品需求或可从本平台 Store 和 Git 重验的来源引用；任意外部候选、手填研发交付与手填 QA 均不受理。下述为后续设计边界，不是已实现能力或授权：

1. **登记与隔离**：由服务端在已登记项目及其冻结 revision、Adapter profile 下接收受限材料，生成内容清单、来源标识和逐文件摘要；限制路径、文件类型、数量及大小，禁止符号链接、路径穿越和执行命令。材料先进入隔离区，不直接写业务仓库或已有 Run 候选。
2. **确定性核验**：从固定工程基线验证文件清单及差异，仅允许批准的源码范围；保护检查及项目规则必须与固定版本一致。复制到新 Run 的独占候选后重新计算摘要并执行登记检查，保存实际结果；校验失败或来源、项目、Adapter 漂移即停止。
3. **事实与人工关口**：材料来源声明、校验报告和负责人确认须分别保存为原生 Workflow 事实，确认绑定完整摘要、项目、适用团队和用途。确认只证明负责人接受输入，不能凭此生成研发已交付或 QA 已放行事实。撤销后新启动和恢复均重新核验并拒绝消费。
4. **团队资格**：外部候选若供测试使用，须先明确研发交付的授权来源及由谁确认；测试团队重新审批用例、执行检查并形成自己的 QA 事实。交付团队只接受平台可核验、同候选版本的 QA 放行、正式规格与受控回执，不能将外部声明或检查日志直接提升为放行。
5. **恢复与失效**：Run 冻结材料摘要、来源、项目和 Adapter 身份，恢复前重读原生确认状态及实际候选，拒绝撤销、内容变化和身份漂移。导入中断须校验既有副本，不覆盖不一致内容；文件投影不成为第二审批或恢复事实源。

落地前仍需确定允许的来源类型与可信证明、材料保管与保留期限、负责人权限、研发交付资格、跨机器可用性及对应失败恢复策略。确认这些选择并补充 OpenSpec、方案决策和负例验证后，才能实现入口；现有能力继续拒绝任意候选导入。

## 团队运行与隔离

各团队使用独立 Mastra Workflow 和 Run。项目选择、方法版本、预算、暂停与恢复沿用平台约束。团队专业状态留在各自 Workflow，公共信封只作投影；测试返工经版本化研发 Port 交接。

测试独立运行须复制并核验来源候选，确保返工不会改动来源 Run；交付核对 QA、候选和正式规格的来源关系后才使用受控 Git/MR 端口。来源 Run 与新 Run 的正式规格分支、候选身份及回执关系须明确设计并通过恢复与并发验证。

项目绑定和原生恢复保护已支持独立 Workflow ID 与初始化路径，专项覆盖多项目及部分原生入口。完整入口兼容和真实环境验收仍以任务记录为准；不能直接将团队子 Workflow 暴露给客户端。
