# 完善研发故障恢复闭环

## 问题

研发阶段失败后，工作台可能要求业务用户确认原样重试，即使用户手上没有可执行的处理动作。后端已有故障、方案版本、修复与工程检查记录，但这些记录无法完整回答某次故障由谁处理、采取了什么动作、复验覆盖了什么。输出校验的重试反馈目前取最近一条故障，可能跨阶段或任务引用。

## 变更目标

- 在研发上下文、方案生成、就绪审查、实施、自检及独立评审中，以证据指导技术故障的恢复。研发团队负责工程修复，平台负责运行依赖恢复，跨团队编排将产品决策交给有权人员。
- 区分已批准业务规则的实现偏差与业务规则自身的缺失、冲突或变更。前者按既定规则修复并回归，后者进入产品澄清，按批准后的版本重新验证受影响范围。
- 用关联记录说明故障、授权内处理动作、复验结果与产物版本。将工作台默认操作集中在有明确决定内容的节点。
- 提供可配置的接续重试上限，继续执行模型调用、时间、工程检查、权限和版本限制。预算耗尽、重复无进展和恢复安全性无法确认均有明确停止或升级路径。

## 设计边界

Mastra Workflow 和 Store 持有恢复事实。平台提供故障采集、预算、并发保护及原生检查点恢复。研发团队在批准范围内诊断和修复，消费项目登记的检查和验收规则。跨团队编排关联平台故障和产品澄清。工作台读取脱敏投影。

策略配置应版本化并绑定到 Run。接续次数默认值由实施时结合当前模型超时、调用预算和离线故障样本确定。配置可选值、复验边界及生效时点应在运行配置和工作台一致呈现。
