## Why

当前平台虽然能把图片 URL 或 data URL 透传给视觉模型，但 C2 仍缺少受控图片资产、媒体治理和可验收的视觉能力，也没有图片生成契约。需要在保持 C1 会话入口不变的前提下，把图片理解与生成收敛为 C2 的独立操作，并先固定数据所有权、安全、幂等和结果交付边界。

## What Changes

- 将 C2 从“图片理解”扩展为“图片理解与生成”能力域，首期定义 `image.understand` 和 `image.generate`，图片编辑继续后置。
- 新增 Runtime 拥有的 C2 操作判别、状态和结果契约；C1 可以作为会话入口，但不拥有图片资产或图片模型执行。
- 新增 `image_asset` 稳定引用和资产生命周期，图片二进制与长期事实分离，当前 `imageUrls` 保持兼容。
- 为图片理解增加媒体校验、视觉模型能力路由、逐图错误、结构化结果和视觉评测要求。
- 为图片生成增加受控参数、模型网关调用、结果落存、内容安全、成本、取消和幂等要求。
- 将当前 LiteLLM 配置拆为对话与图片两个平台别名和两把服务端上游 key；Runtime 只接触平台别名与 `LITELLM_MASTER_KEY`。
- 要求图片生成完成后以资产引用回填会话；禁止把 base64、provider 临时 URL 或签名 URL当作稳定消息事实。

## Capabilities

### New Capabilities

无。C2 仍属于现有 `ai-platform` 稳定能力范围，不因内部图片能力扩展提前拆分服务级 spec。

### Modified Capabilities

- `ai-platform`: 扩展 Conversation Run 的多模态行为，新增 C2 图片操作、`image_asset`、图片结果交付及其安全、幂等和质量约束。

## Impact

- Runtime：输入判别、图片应用服务、Run/Message 结果、幂等与取消。
- 连接器与存储：媒体校验、资产元数据、图片二进制存储和短期访问地址。
- 模型网关：视觉与生图模型能力目录、图片模型调用、配额和错误映射。
- 渠道：图片操作入口、上传进度、生成状态、逐图错误和图片结果展示。
- 治理与可观测：敏感图片脱敏、内容安全、视觉计费、生成成本和 C2 评测。
- 兼容性：现有无 `operation` 的 C1 Run 和 `imageUrls` 输入行为保持不变；新能力必须通过显式 C2 操作或受控内部调用进入。
