# 按任务选用的交接检查

只读取本次有关部分。以下是信息要求，不是固定PRD目录或数据库模式。业务示例仅解释检查方法，不是目标项目的默认政策。

## 内容导航

- 新需求与范围：功能完整性检查、正式输出覆盖。
- 页面与数据：字段级定义、按钮与操作授权、页面规格与规则归位。
- 共用机制：公共规范的归属与表达。
- 规则联动：状态与非常规链路、身份与历史、指标与阶段证据。
- 正文复核：审稿判断示例、完成前的反向阅读。

## 功能完整性检查

形成或变更新功能时，先沿业务路径检查下列维度，再按现有交付结构编写。检查维度不等于强制章节或要求用户逐项回答；无实际关系的项目不扩展成需求。

| 维度 | 默认主动核查 | 处理边界 |
| --- | --- | --- |
| 目标与范围 | 谁遇到什么问题，本期改善什么，哪些能力已确定延期 | 不替用户新增业务目标或版本承诺 |
| 对象与页面 | 操作哪个记录、关系和唯一性，入口、列表、输入、详情及必要弹窗是否覆盖 | 沿用已有交互；缺少核心行为定义主动补齐，不为套页面模板新增页面 |
| 输入与数据 | 来源、默认、必填、可选范围、校验、回填、修改及历史 | 有依据的规则直接整理；缺少业务取值或关联政策先形成决策问题 |
| 权限与责任 | 访问范围、动作资格、责任指派、状态条件及提交时变化 | 查看、修改、下载等分别判断；不自行扩大授权 |
| 流程与结果 | 起始事实、人工／自动动作、状态变化、成功返回、任务解除和通知 | 不用抽象“处理成功”替代实际改变；自动转换和新状态须有依据 |
| 异常与历史 | 空态、校验拒绝、失败保留、并发、取消／终止／恢复、换人和旧数据 | 选择与该功能有关的异常；保留输入、部分写入及恢复策略按既定规则，缺失会改变业务结果时先确认 |
| 依赖与运行 | 公共机制、外部事实、配置前提、敏感数据生命周期及适用响应目标 | 引用真实有效资料；不凭经验编造性能数值、保留期或外部能力 |
| 验收与效果 | 正常、边界和拒绝场景的可观察结果，功能质量与效果目标是否分开 | 补已有规则的验收，新的成功门槛先确认；不把人工评估新增为系统功能 |

发现缺口时在内部按“已有依据可直接完善／需要业务选择／实施与验证待执行”处理。同一规则在多个位置出现时先确定权威来源；确认答案后一次同步关联定义。项目已有配套资料先复用，不为每次检查新建一份缺口清单。

## 正式输出覆盖

以已确认本期范围、能力归属及实际页面为检查起点，逐项定位正式需求章节和验收依据，包含适用的平台支撑与基础资料。内部字段文档、故事或总览中的提及不能代替正式页面输出。核心展示、输入、按钮资格、反馈和返回应在正式正文直接理解；共用规则可准确引用。组合权威章节生成正文时复核顺序、重复、节号、锚点和内部追踪残留，生成成功不能代替阅读评审。

例如招聘已输出但人员管理只存在内部配套，人员在本期需要实现时，应补正式需求阅读单元并同步交付入口、招聘依赖及验收引用；不能仅因已有人员字段文件判为交付完整。未进入本期的完整员工管理不因检查而扩大范围。

## 字段级定义

| 信息 | 需回答的问题 |
| --- | --- |
| 语义与关系 | 表达什么事实，属于哪个对象，单值／多值，引用哪个对象？ |
| 来源与生成 | 人工输入、外部事实、系统产生或推导？谁提供？拿不到如何处理？ |
| 准入 | 默认、必填条件、选项、公共格式引用、跨字段约束？ |
| 变更 | 谁何时可改，是否需原因，影响哪些状态、权限、任务及历史？ |
| 治理 | 查看／修改／下载／导出范围、敏感性、版本及生命周期依据？ |
| 交接 | 页面动作、故事、验收关系？哪些已有依据，哪些需选择？ |

已有联系方式格式不能代替业务是否必须录入联系方式；“时间”不能代替计划、实际、录入时间的区分。不为填满表编造政策。公共参数暂存公共文件时先保留单一权威位置，迁移时同步引用。

## 按钮与操作授权

记录页面、对象动作、角色、范围、责任、状态／前置事实、展示及可用条件、确认、成功／失败反馈和验收。菜单访问、页面查看、数据可见、按钮可执行及服务端准入分别判断。

隐藏还是禁用由项目交互政策决定，不将某项目方案提升为通用规则。查看、修改与下载分别核查；多角色按项目定义的合并方式判定，不自行决定权限相加或同角色依赖。页面打开后权限／指派／状态变化仍复核。是否允许人工覆盖自动结果须有业务依据，按钮矩阵不意味着需要自定义权限配置器。

## 页面规格与规则归位

页面需求以实际按钮、字段和可观察结果组织，按目标页面选择列，不机械填满模板或编造默认值。优先遵循项目已有的表头规范，同类页面表头及列职责跨模块一致；项目未另定结构时，采用以下写法：

- 输入字段：字段名称、业务含义、数据类型、控件类型、取值来源、默认值、必填条件、校验规则、修改与历史独立分列。默认值用于新增或首次输入，纯编辑可标不适用，回填归修改与历史；数据类型不代替控件或展示样式，来源不代替可选值；取值来源应写明字典／关联对象、可选范围及必要枚举。
- 筛选项：字段名称、数据类型、控件类型、取值来源、默认值、筛选规则独立分列；明确匹配方式及条件组合。共用查询和分页维护一处，页面只定义排序、计数、特殊筛选、空态与业务例外。
- 展示字段：字段名称、数据类型、取值来源、展示规则、空值展示、交互说明独立分列；链接写明跳转目标，按钮写实际动作。展示占位不回写数据，不用0、当前时间或默认状态替代未知事实。
- 按钮：按钮名称、所在位置、操作权限、前置条件、点击行为、确认要求、成功结果、异常反馈独立分列。一行一个实际动作；关闭／恢复、指派／换人等条件不同的动作分别定义，拆行不意味着新增按钮或改变原交互载体。工程编号及场景追踪放验收附件，按项目规则保留内部溯源。

有筛选区按“筛选项→按钮→列表字段”组织，无筛选区按“按钮→输入／展示字段”组织。同页相邻定义不再加“见本页按钮表”“见下方字段”等导航；跨页／跨章节的必要引用用准确业务名称及锚点，不能替代当前页面的核心行为。

新增按钮定义目标页及按新增默认值初始化，编辑按钮定义目标页、当前记录回填及资格；字段表定义只读、隐藏、必填和修改限制。保存按钮分别明确创建记录或更新当前记录、确认、成功返回及失败处理。普通新增／编辑不另维护完整模式对照表；不同角色、授权、状态或历史影响仍须明确，不能一概归为“空白与回显”。接口名称及实现方式留给技术设计，无已确认契约时不在PRD编造接口。

格式、唯一性及跨字段约束归对应字段；保存触发的事实确认、后果确认、失败反馈归保存按钮。不要再用“保存校验／确认”汇总表重复两处已有信息；复杂确认弹窗确需独立说明时，就地定义弹窗输入、按钮和结果，避免把所有内容挤成长单元格。

跨模块公共规则唯一维护；模块特有且多页共用的业务规则在模块内对应业务章节定义，按钮仅引用复杂共享条件并保留本页准入与结果；单页特殊规则就地定义。角色章说明整体范围，不再维护平行按钮资格清单。图示的必要符号、范围或异常说明可以保留，正常阅读提示及重复正文不机械追加。

复核时实际推演新增初始化、编辑回填、只读字段、保存确认／拒绝、成功返回和空值展示；删表或移动内容后核对业务约束、稳定锚点、编号和验收关联未丢失。列拆分和预检通过不等于业务完整或实现通过。

## 公共规范的归属与表达

公共规范系统复审应阅读实际正文及代表性引用页面，检查归属、适用范围、规则粒度、重复与冲突、异常闭环及验收承接。不能只修截图中的一列或一次性换表头。

### 判断规则放在哪里

| 规则性质 | 权威定义与正式呈现 |
| --- | --- |
| 同类输入格式、提交保护、通用反馈 | 公共规范；页面明确适用字段和业务准入 |
| 某业务特有的数量、顺序、时长或状态约束 | 该模块的字段或业务章节，不因暂存公共文件而成为全系统默认政策 |
| 平台共用能力的完整操作规则 | 对应管理功能连续呈现，使用方保留必要的字段选择、准入和反馈；跨模块规则仍按项目约定保持一个权威源，可生成组合，不能手抄成平行副本 |
| 授权、审计、生命周期 | 公共机制与模块例外分别定义；区分访问权、历史保留及业务状态，术语及判定保持一致 |
| 性能、容量与恢复 | 运行要求，说明负载、目标、计时／恢复口径和验证结果，不混入输入格式 |
| 测试覆盖和执行状态 | 验收附件或执行记录；不把“各表单须逐项测试”等检查过程写成页面行为 |
| 维护方法、候选方案及后续范围 | 内部协作或已确认版本计划；当前适用范围不列尚未交付模块 |

### 按信息维度选列

表头以项目现有规范为准，下表是用途示例，不要求每份文档都建立全部表格。

| 内容 | 适合独立表达的维度 |
| --- | --- |
| 基础输入校验 | 规则对象、适用范围、长度／取值、校验与处理 |
| 附件准入 | 规则项、准入要求、保存与反馈 |
| 提交及并发 | 场景、提交判定、结果与反馈 |
| 操作授权反馈 | 条件／场景、页面反馈、服务端准入与结果 |
| 审计信息 | 审计信息、记录内容、记录约束 |
| 响应目标 | 操作、负载条件、时间上限、计时范围、成功判据；共用负载可在表前一次定义 |
| 备份恢复目标 | 项目、目标、判定口径、恢复范围／要求 |

一行聚焦一个规则对象或判定场景。长度、格式、必填、唯一、展示、安全和历史影响是不同维度；复杂密码、附件或授权规则可独立成短阅读单元，不靠新增“其他说明”列容纳全部内容。简单单一规则仍可用两列表或短段落，不为拆列制造大量空白。

### 复审后的完成判据

- 将末尾“追加／补充”条款并入对应规则，检查原表、补丁、页面及验收是否给出相同结果；重复出现不代表规则已传播完整。
- 校验适用性：邮箱格式不自动意味着所有邮箱唯一；某表单联系方式必填不自动适用于所有人员；必填文本裁剪不自动适用于密码；示例以项目已确认政策为准。
- 修改表达时保持已确认参数、单位、边界及作用范围；移出业务参数时核对接收字段及验收，不能删去上限或扩展适用对象。
- 授权概念或当前政策变化时，复核摘要、页面、字段、异常及验收中的旧说法；名称、历史作者及保留事实不代替实际授权判定。
- 按影响选择边界、原关联保留、新选择、提交时变化、并发失败、撤权与恢复等案例，明确输入、动作、结果及证据；这些是文档推演，不是实现测试。
- 生成后重新阅读实际输出，检查引用、定位、版本及业务文字。结构校验和自动预检只报告其检测结果，不据此声称技能行为或产品效果已验证。

## 状态与非常规链路

按“起始事实→动作及执行人→前置条件→状态／数据结果→任务和提醒→历史／审计”描述。根据实际范围选择取消、替代、换人、缺失、迟交、并发、终止及恢复案例。

例如两条重复记录都有活动任务：先查发生证据及合并支持范围。若项目已选事前拦截，不擅自新增自动合并、自动终止或整体开发阻塞；真实旧数据问题作为局部决策。

## 身份与历史

身份、账号、角色、组织和业务责任不是同一概念。多人协作时核查同人多角色、改名／标识更正、禁用、角色移除、责任替换；一人几账号、是否无账号人员由项目决定。

历史作者不等于当前访问权；账号恢复不等于业务恢复；负责人变更不重写原作者。案例预期不唯一时标记对应概念部分定义，不笼统称已解耦。

## 指标与阶段证据

指标明确事件、单位、起点、窗口、分子／分母、排除及无样本处理；测量目标不自动变成状态阻断。消息总数一致不代表对象正确，按项目触发规则核对对象和日期。

排期依赖容量、负责人、外部窗口和估算，未知时给成果顺序及退出条件，不承诺日期。案例已写、工具检查通过、代码测试执行、业务效果达标分别提供证据。

## 审稿判断示例

用下列场景检查判断方式。具体角色、流程和交付形式以目标项目为准，示例不授予新业务规则。

| 收到的内容 | 要先查什么 | 应采取的行为 |
| --- | --- | --- |
| “本节以产品决策X为准” | 这是内部源还是正式输出？当前章节是否直接定义了规则？ | 内部保留追溯可以合理；正式正文移出过程引用，补足实际条件。查找同类残留，不能未定位就承认输出有错。 |
| “试点建立基线，指标达标后通过” | 指标属于系统功能、质量要求还是效果观察？通过是测试、试点还是发布？ | 保留已确认目标，区分测试依据与效果判断。没有建设指标功能时，不把人工测量工作写成研发需求。 |
| “已有字段文档，模块完成” | 本期页面是否有展示、输入、动作和反馈？正式读者拿到哪些文件？ | 内部信息齐全不等于对外交付。按已有结构补核心正文，不要求读者拼十几份文件。 |
| “停用值不能保存” | 新记录、新选择，还是原记录编辑其他字段？原规则是否区分这几种情况？ | 三个案例分别推演。规则未确认时不能靠常见做法决定；已确认但正文混淆时按原政策重写并核对验收。 |
| “专业性不够，AI味太重” | 是否反复写已确认、不新增、按某规则，是否模板标签或图表替代了定义？ | 分别检查读者用途、业务事实、结构、语句和案例；清除过程用语，但保留必要禁止项、范围及真实依赖。不是统一换词或再加一份清单。 |

### 完成前的反向阅读

暂时不看聊天与内部决策，按交付入口阅读一条完整业务路径：

- 能否指出实际执行角色、当前记录和操作入口？只知道角色名却不知道记录范围，不算授权清楚。
- 字段未填、选项停用、资格变化、保存失败时，能否确定是否写入及留在哪里？只写“公共规范处理”而没有业务结果，不算异常闭环。
- 操作表、字段定义、状态图和验收是否给出相同结果？同一条件出现不同措辞时查实际语义，不只做字符串一致检查。
- 未决项是否影响当前动作、何时必须落实？“以后补齐”不是可执行依赖，“尚未实现”也不是需求缺口。
- 读者需要反复跳转才能拼出同一功能时，优先调整现有正文的顺序和局部定义。只有实际受众或独立维护责任不同，且项目允许时才考虑新增文件。

上述是文档推演，不是实际用户测试。若做技能效果评估，应让执行者仅凭技能及最小原始材料完成真实任务，再检查产物和遗漏；结构校验或上述自查不能证明未来每次都能主动发现问题。
